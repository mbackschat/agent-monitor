# Architecture

## Purpose and status

Agent Monitor maps heavy processes to specific coding-agent sessions. Sampling and attribution must be reusable by text output, an optional terminal UI, and a native menu bar app. See [PLAN.md](../PLAN.md) for open work and scope, and the [development guide](development.md#validation-coverage) for validation limits.

## Current implementation

`AgentMonitorCore` owns native process inspection, resource measurements, metadata parsing, process-lifetime history, threshold filtering, and attribution. Models are `Sendable` values. The monitor is owned by a sequential sampling loop; the core has no terminal UI or SwiftUI dependency.

`AgentMonitor` owns Apple Argument Parser options, validation, and output selection. `AgentMonitorCore.MonitoringSession` owns baseline acquisition, sequential sampling, enrichment, and immutable `MonitoringSnapshot` publication. Its `@concurrent` run method keeps native inspection off the main actor. It awaits each consumer before collecting again, preventing a backlog. Cancellation and collection/consumer errors propagate. An optional async threshold supplier is read once per sample before enrichment and filtering; the resulting snapshot records those same thresholds. The TUI supplies its main-actor-owned requested values, and a pending label distinguishes them from the last applied snapshot. An optional `LiveInterval` lets the host change the interval while the session waits: setting it wakes the wait, which counts the time already waited against the new interval, so a shorter interval applies without waiting out the old one and an unchanged one costs a single wake per sample. The snapshot records the interval used; CPU uses measured intervals rather than the configured wait; newborn windows have the bounded scan skew described below. Freezing is presentation state only: `LiveReportState` keeps its snapshot and holds the latest received one until unfrozen, while sampling continues. The sampling baseline and process history survive updates; text/JSON callers keep their configured thresholds and interval.

`AgentMonitorPresentation` owns text output, JSONL encoding/schema, and UI-independent sorting, process selection, disclosure, and compact report layout. `AgentMonitorTUI` alone depends on the regular, unmodified SwiftTUI package and maps presentation lines to terminal views. The UI owns keyboard input and the runtime lifetime; its lifecycle task consumes the same monitoring session as the CLI.

`SessionGrouping` derives neutral launch-session groups from the already-filtered snapshot and counts each process lifetime once. Exact groups use provider plus session ID; unresolved entries use process lifetime. A child is assigned to a root only when the current snapshot corroborates an exact root-thread attribution for the same provider and runtime lifetime. Otherwise it stays in its exact-session group. No directory/TTY/shared-runtime heuristic supplies identity, and no extra process collection or provider control requests occur. Missing measurements produce explicitly partial sums of known values; all sums cover heavy findings only.

`LiveReportState` owns typed process/group selection and disclosure for both interactive views. A filtered snapshot cannot distinguish a temporarily quiet workload from an exited one. Group expansion therefore follows the exact provider/session or unresolved process-lifetime identity across absence; active `openGroups` contains only current or pinned groups, while up to 256 absent identities retain expansion in most-recently-expanded order. Visible/pinned expansions are never evicted by that bound. Explicit collapse removes the remembered choice. Disclosure memory retains identities only, never measurements or executable action state.

Process inspection remains limited to one active process (native inline details or the TUI pane): disappearance clears its visible process and scroll offset, retaining only one pending PID/start identity. That exact process restores its details and report selection on return unless the user selects another row, changes disclosure/grouping, minimizes/restores the pane or opens an action panel. A reused PID cannot inherit it. Automatic fallback selection while the process is absent does not cancel restoration; keyboard focus is not assigned by restoration. The existing details mode and split survive filtering. Collection reset (including native dismissal) clears disclosure memory. Text and TUI reuse the grouping projection; JSONL's flat snapshot and schema stay unchanged.

The shared table formatter pads headers and fields explicitly, reserving a marker cell after each numeric column (`*` for an exceeded process threshold, `~` for a partial group total). The name-only process column fits the longest process name across the current findings or its heading, whichever is wider, up to the viewport-dependent cap. Measuring across findings keeps scrolling from changing column positions. Unused process space goes to provider/session identity and then terminal/project information; short names no longer absorb spare terminal width. Compact views omit the terminal/project column and split the remaining width between process and agent/session, abbreviating oversized names so they cannot push identity out of view. Group headers retain the heavy-process-only totals qualification.

`LiveReportState.setSessionDisclosure` applies explicit bulk expansion/collapse to the current presentation level. Top-level targets are displayed session groups (including pinned groups); a nested process targets only its containing group. Hosts supply the focused/selected identity and the native singleton-flattening policy, without provider recognition. Individually pinned processes and flattened native singletons are top-level, unavailable/hidden targets cannot supply child scope, and actions block the command. Collapse moves a hidden selection to its parent and clears hidden process details, preventing subsequent sampling from reopening the group to reveal a stale selection. Bulk operations update the same bounded disclosure memory and never open multiple process inspectors.

## Attribution evidence and inspection scope

Each finding identifies a process lifetime, its usage, available working directory, provider session/thread ID, runtime PID and terminal when known, and the evidence supporting that association. Only heavy processes appear; smaller ancestors supply tracing context.

- **Codex:** child `CODEX_THREAD_ID` / `CODEX_SESSION_ID` markers identify logical threads and their root session. Open writer-lock descriptors can identify a thread when exactly one candidate exists in the nearest native runtime. With no observed runtime ancestor, a marked workload is linked back to the one live Codex runtime holding a writer descriptor for its exact thread ID, provided that runtime started no later than the process carrying the marker. A matching root-session ID alone is insufficient; multiple matching runtimes leave the runtime unresolved while preserving the marked thread. A runtime started later, including one resuming the same thread, cannot establish launch origin.
- **Claude Code:** `CLAUDE_CODE_SESSION_ID` identifies launch origin. Native `claude` executables and the versioned native installation are recognized as runtime boundaries only when invoked as themselves: the same executable runs embedded tools selected by `argv[0]` (observed: `ugrep` behind the Bash tool's `grep`), so an `argv[0]` naming neither `claude` nor the executable withdraws the runtime claim and the process resolves as a workload through its own marker. Unreadable arguments keep the executable claim. Native runtimes carry no marker of their own, and platform-binary children such as Bash-tool shells expose no environment; both join the session that `claude agents --json` lists for their runtime through the [harness session registry](#harness-session-registries). See [runtime attribution research](research/claude-runtime-attribution.md). A workload detached from its runtime (for example a background job whose shell exited and which was reparented to launchd) is linked back to the one live Claude runtime that listens on the inbox socket named by its `CLAUDE_CODE_MESSAGING_SOCKET`, provided that runtime started no later than the process carrying the marker; a later start means PID and socket-name reuse. The adapter requests native listening-socket paths for recognized runtimes; detached candidates enter enrichment in a second pass after the marker is known. npm-based Claude roots have not been validated.
- **Historical ancestry:** parent relationships survive observed parent exit. PID plus microsecond start time prevents PID reuse from inheriting a different process's history.
- **Nested agents:** one agent started inside the other (Codex → `claude`, or Claude → `codex exec`) leaves both providers' markers in its workloads. The inner agent is the nearest runtime above the workload and set its own marker last, so its provider's marker attributes the workload; a detached workload carrying both stays ambiguous.
- **Uncertainty:** multiple runtime thread candidates, conflicting markers, and incomplete metadata remain explicit. A known runtime/terminal can still be reported when the logical thread is unresolved. Unresolved agent-associated heavy consumers remain visible; unrelated unknown consumers require `--all-processes`.

The monitor retains the complete adapter recognition set with each process lifetime while its executable path is unchanged; executable changes invalidate that set and metadata. A read `argv[0]` can only narrow the set for that lifetime through the adapter's invocation check, without repeating path recognition, and an unreadable later read keeps the earlier invocation. A per-snapshot index contains only live runtimes claimed by exactly one provider. Adapter path parsing supplies explicit URL directory hints, avoiding filesystem checks during recognition; the host remains the native I/O boundary. Detached lookup uses that index without re-recognizing every process for every query. Session markers, descriptors and sockets still refresh through the native reader; resolved session ownership is not cached.

Detached runtime candidates are enriched in a second pass after reading the workload's marker. Every enrichment refreshes all eligible candidates, including after a prior match, so a closed descriptor or competing runtime cannot leave a cached association in place. Sampling and action lookup share this path; it does not invent parent edges in the reported ancestry.

The Codex adapter identifies a process as a **shared runtime** only when it is the attributed Codex runtime itself (matching PID and start time), has no exact thread, and carries ambiguous evidence with more than one distinct writer thread ID. This uses existing snapshot evidence; it does not reinterpret unresolved descendants as shared runtimes or change the JSONL contract. The runtime remains a singleton in session grouping because its own resource usage cannot be allocated among the hosted threads. Exact workload markers keep precedence over this label. No terminal or client association follows from the label.

These are **launch-origin associations**, except `sessionRegistry` evidence, which names the session a runtime hosted when its harness listed it. A Gradle, Kotlin, MCP, or other shared daemon can later serve different sessions; its inherited marker does not establish which session caused its current CPU usage. Desktop hosts are labeled nonterminal where identifiable, with no promise of desktop conversation attribution. A terminal-less detached worker can retain a known logical session even when its runtime is unavailable.

The monitor examines only same-user processes. It reads allowlisted session markers, permitted process metadata, and Codex writer-lock descriptor paths, and may run a harness's declared session-listing command; it does not read conversation transcripts or keep full environment buffers. History exists only in memory for live processes and their necessary ancestors. Monitoring after an unmarked process has already detached may not recover its session.

## CPU accounting

CPU is averaged between snapshots in the one-core unit (100% = one logical CPU). Each native snapshot records its listing time `L(k)` immediately before `proc_listpids` and its scan duration. Listing times, each lifetime's sample time `t`, cumulative user+system CPU `C` and birth time `b` from `ri_proc_start_abstime` use the reader's same Mach timebase conversion; Mach absolute time excludes sleep. The BSD wall-clock start remains part of exact PID-plus-start identity and is never compared with these measurement times. `exec` preserves that identity and cumulative accounting.

| Observation | CPU percentage |
| --- | --- |
| Same lifetime observed in the preceding snapshot with valid counters and positive sample-time delta | `100 × ΔC / Δt`, unchanged. |
| First observed now, born after the preceding listing | `100 × C / (t − L(k−1))`. |
| First observed now, born at or before the preceding listing | Unavailable; subsequent valid observations use normal deltas. |
| First snapshot | Unavailable. |

Newborn CPU uses a zero baseline at the previous listing, rather than process age or the configured wait. Its window can exceed an existing lifetime's window by at most the previous scan duration. A lifetime absent from the preceding snapshot cannot reuse an old counter retained for ancestry. Missing or decreasing counters and nonpositive deltas do not produce CPU values. Lifetimes never observed and CPU after a lifetime's last observation remain uncounted; exited-descendant recovery is deferred and child counters are unused. Existing threshold, attribution, history, icon and session-group aggregation rules remain unchanged; their values incorporate these measurements.

## Boundary for multiple presentations

```mermaid
flowchart TD
    OS[macOS process APIs] --> Core[Sampling, history, filtering, attribution]
    Core --> Session[Monitoring session: immutable snapshots]
    Session --> Text[Text renderer]
    Session --> JSON[JSONL encoder and schema contract]
    Session --> TUI[Optional terminal UI]
    Session --> GUI[Native menu bar UI]
```

The monitoring session owns cadence, baseline acquisition, metadata enrichment, cancellation, and snapshot publication. Snapshot values carry timestamps, measurement semantics, process identities, resource usage, and attribution evidence. UI code consumes them without inspecting processes itself. Sampling must not block keyboard input or native UI interaction, and slow rendering must not create an unbounded snapshot backlog.

Snapshots are neutral, immutable, `Sendable` structures with typed identities, numeric measurements, timestamps, session associations, and evidence. They contain no terminal escapes, display strings, widgets, or Argument Parser types. Text, TUI, and JSONL are peer adapters over the same monitoring results, not separate collectors. The CLI loop and report envelope have been extracted; adapters consume the same neutral snapshot.

The JSON adapter owns serialization and the versioned wire contract. `--json` already emits one compact report per line; `--json-schema` emits its schema and exits without collection. Keep schema examples and validation tied to actual encoded snapshots so documented fields and runtime output cannot drift. Generated CLI help should describe defaults, measurement units, streaming behavior, and schema discovery. Neither JSON encoding nor help generation belongs in the collector.

Presentation owns layout, colors, text formatting, keyboard or pointer input, selection, scrolling, and disclosure. Selection and disclosure use process identity (PID plus start time), so sorting or PID reuse cannot silently switch the displayed process. If a process disappears from the findings, clear its details and show a notice while preserving pane geometry. A view refresh does not trigger extra CPU measurements.

Lines carry display roles rather than colors (`ReportLine.Style`): the status line is `title`, filters, key hints and panel notes are `muted`, heavy rows are `heavy`, the selection and details divider are `selected`/`separator`, and action panels add `warning`, `success` and `failure`. The SwiftTUI adapter maps roles to blue, gray, yellow, cyan, green and red; `NO_COLOR`, or `--no-color` passed to the host as `NO_COLOR`, removes them, and the README preview approximates them. Text reports and action commands carry the same roles; `ANSIText` encodes them as basic SGR colors that follow the terminal theme, and the CLI applies them only when the output descriptor is a terminal and neither `--no-color` nor `NO_COLOR` is set.

Text, TUI, and GUI share measurement and attribution results. Their rendering and interaction code remain specific to each interface. A SwiftUI-like terminal library does not itself guarantee reusable native SwiftUI views. Any reusable presentation state must remain free of terminal control codes and UI framework types.

Session-group project labels use displayed workload working directories, excluding the runtime’s own directory when workload rows exist. A shared runtime is labeled without a project claim. More than one distinct readable workload directory produces “Multiple directories”, including nested paths; no project-root inference is made. Otherwise, missing workload directories produce “Unknown project”. Native subtitles and wide TUI rows do not substitute a shared runtime’s launch directory for workload evidence. Runtime directories remain available in details. Directory labels are presentation only and never alter provider/session identities or attribution confidence.

## TUI contract

- Leave mouse reporting disabled through SwiftTUI's public host configuration so the terminal owns drag selection and copying. TUI navigation remains keyboard-driven. The PTY smoke guard rejects mouse-reporting enable sequences in both color and NO_COLOR modes.

- Launch explicitly with `--tui`; accept the user's suggested `-tui` spelling as an alias. The existing default text report and JSON mode retain their behavior.
- Use the terminal window and refresh in place. TUI mode watches continuously unless an explicit `--samples` limit is supplied; `--interval` keeps its sampling meaning. Reject simultaneous TUI and JSON output or a noninteractive output stream with an actionable message.
- Show only heavy processes in a compact table: process/PID, CPU, footprint, provider/session abbreviation, terminal, and project when space permits. Preserve explicit unknown and ambiguous labels. Highlight exceeded resource values and the selected row; meaning must also be readable without color.
- Stable arrival order is the default; `o` selects it. Offer CPU, footprint and PID sorting through `c`, `m` and `n`; `r` reverses numeric sorts and has no effect on Stable order. Show the active sort and applicable direction. Use stable process identity as a tie-breaker; preserve selection and disclosure by PID plus start time when sorting or refreshing, rather than by row index.
- ↑/↓ selects a row; → expands and ← collapses disclosure containing the full session ID, directories, runtime, ancestry, and attribution evidence. Keys `[` and `]` scroll long details. Full arguments remain governed by the existing `--commands` option. `q` or Ctrl-C exits and restores the terminal.
- Separate the details pane with a full-width rule and allocate its height from a remembered content-area ratio, independently of row counts, text length, or disclosure content. Start minimized; → opens at 50% initially. `-`/`+` adjust by five percentage points within 10–90%; `0` minimizes, `9` maximizes, and `=` restores the remembered ratio. These modes do not overwrite the ratio. Minimum pane heights take precedence in small terminals. Pad each pane to its allocation and constrain each rendered line to one terminal row. Open details follow explicit row selection; disappearing processes clear content without moving the divider.
- Adapt chrome to the terminal width: one header row at 120 columns and above, two at 85–119, and three below 85. These width-based header allocations keep pane geometry stable as counters, notices, and pending filters change. Shorten oversized status text with an ellipsis while retaining filter values. Pack complete key groups onto shared rows where they fit; split an oversized group only between whole controls. Derive table/details heights and detail-scroll limits from the same actual header/footer row counts. Very small viewports retain a bounded resize hint and quit control.
- Handle resizing and preserve selection across updates. Disclosed shared-daemon associations must retain the launch-origin qualification.

## Verification boundary

Core tests continue to use deterministic observations and native measurement checks. The extracted session needs cadence, cancellation, and error tests with controllable inputs. Presentation tests cover selection identity, disclosure, unknown/ambiguous states, and narrow layouts. A real terminal test must verify refresh, resizing, input responsiveness, and terminal restoration. Measure TUI overhead separately from the existing collector result.

The isolated SwiftTUI runtime passed terminal interaction checks; [TUI research](research/terminal-ui.md) records the host behavior and measured probe overhead behind the adoption decision. Integration has dedicated presentation tests and a PTY journey. The native menu bar app consumes the same contract with separate SwiftUI rendering and AppKit lifecycle ownership.

## SwiftTUI host evaluation

The completed [isolated probe](research/terminal-ui.md) used SwiftTUI 0.14.0’s public `RunLoop` with a `TerminalHost`, input reader, signal reader, state container, and focus tracker. This bypasses the high-level scene launcher’s mandatory discovery socket without modifying upstream code. SwiftTUI still owns raw mode, rendering, focus, input, resizing, and cleanup; the application owns the runtime lifetime. No browser or discovery service starts.

The monitor uses the same public host with neutral presentation state confined to the main actor. SwiftTUI is declared as an exact remote package dependency in the main manifest. `swift build -c release` compiles the unchanged upstream sources with standard compiler optimization; no custom framework build or fork is maintained.

## Process and session actions

`AgentMonitorActions` depends only on the monitoring core, Foundation/Darwin, and AppKit's `NSRunningApplication` for finding and activating terminal applications. `ProcessActions` exposes asynchronous termination, message preparation and submission, and terminal focus to the UI; `AgentMessaging` separates provider recipient verification from message acceptance; `SessionActions` selects the Codex or Claude adapter by the attributed provider. `SessionActions` runs native/provider work off the main actor. `ActionPanel` in presentation owns the frozen process, recipient choice, draft, review and result; SwiftTUI maps inputs and owns one cancellable action task. Sampler cadence, text/JSONL output and the snapshot schema remain read-only and unchanged.

`MessageDraft` formats the shared outgoing context: sanitized process name and PID, CPU (100% = one core), decimal-GB memory footprint and optional ISO 8601 sample time. `ActionPanel` captures the selected snapshot time before asynchronous recipient preparation and attaches it to the verified draft; newer reports never rewrite that observation. Missing values remain explicit, including time/CPU for direct-PID CLI observations. Copying in the native host uses the same message formatter as review and submission, has no provider side effects and is available only during compose/review. Native clipboard writes stay on the main actor and are injectable for tests.

Termination rechecks same-user ownership, PID/start time and executable directly before SIGTERM. Messaging obtains a fresh ancestry/metadata observation, independently of display thresholds through `Monitor.finding(for:)`, and compares attribution with the frozen process. It requires a live runtime and exact session UUID; detached historical evidence alone fails closed, and `sessionRegistry` evidence is not accepted because the inbox comes from the workload's marker. Native identity checks and the eventual OS/provider mutation are separate operations, so they cannot eliminate every race.

The Codex adapter uses a bounded `codex app-server proxy` connection with a validated WebSocket upgrade and masked client frames (the proxy forwards raw socket bytes, not JSONL), initializes the protocol, and calls `thread/read` with `includeTurns: false`. The selected thread's live `sessionId` supplies the root; idle/active status permits a recipient, while unloaded/error/unknown states do not. An inherited root marker must agree. The adapter repeats verification before submission and uses `codex queue --remote unix:// --thread <UUID> --message <text>` on the same default local endpoint. It does not resume threads, subscribe to turns, read full transcripts, start servers or retry uncertain submissions. Calls use argument arrays, a ten-second deadline and a one-megabyte output limit; fragmented text and ping/pong follow RFC 6455, while unexpected frame types/extensions fail closed. Cancellation closes the owned CLI subprocess. Provider stderr/output is not persisted or displayed.

The Claude adapter verifies the live binding with `claude agents --json`: exactly one entry must carry the attributed runtime PID, its `sessionId` must equal the attributed session, and its status must be `busy`, `waiting` or `idle`. This catches `/clear` or `/resume` rebinding a runtime after its children inherited an older marker. The inbox path comes from `CLAUDE_CODE_MESSAGING_SOCKET` in the same environment as the attributing `CLAUDE_CODE_SESSION_ID`; the parser keeps it on `SessionMarker`, and `Monitor.attributingMarker(for:)` exposes it to actions without adding it to snapshots or JSONL. Each verification and send reads that environment afresh and requires a non-symlink socket owned by the user. The adapter writes one stream-json user line without the documented auth line: the session token marks the session's own children, whose messages bypass the peer controls that should govern an external monitor. Connection failure before the line is written reports that nothing was sent; the inbox sends no acknowledgment, so end-of-stream after the write is the acceptance signal, and a timeout afterwards is uncertain. See [Claude session messaging research](research/claude-session-messaging.md).

Terminal focus is adapter based. `TerminalFocus` reads the runtime's current controlling terminal and the nearest regular application above it (`NativeActions.terminalHost`, revalidating PID and start time), then routes by bundle identifier to a `TerminalFocusAdapter`. An adapter receives only the `/dev/ttysN` device path and the host application, and returns whether a session owns that device; it may select, unminimize, order and activate, never type, run commands or read screen contents. A host without an adapter is only activated through `NSRunningApplication`, while an adapter that finds no session fails instead of activating, because another window could show a different session. `TerminalAppFocus` is the first adapter: a fixed AppleScript run by `osascript`, with the device path passed as `argv`. The router and protocol live in `Sources/AgentMonitorActions/TerminalFocus/`, one adapter per file under its `Adapters/` folder, registered in `TerminalFocus.local()`. Adding iTerm2, WezTerm, kitty, Ghostty or tmux means adding an adapter (or, for tmux, a resolution step before the lookup); see [terminal focus research](research/terminal-focus.md).

The `kill`, `message` and `focus` subcommands reuse `ProcessActions` through `ActionRunner` in the CLI target. `NativeActions.process(pid:)` replaces row selection: it observes the PID's current lifetime and attribution, independently of thresholds, and that observation is the frozen identity the actions recheck. Confirmation is a `[y/N]` prompt on an interactive stdin, or `--yes`. `ActionFailure.uncertain` marks a request that may have been accepted; the CLI exits with status 2 and the TUI shows it as a warning instead of a failure.

Cancel and reap owned provider subprocesses on shutdown. Root is the default message recipient; an unavailable root must fail without falling back to the selected child. The UI requires a separate Ctrl-Y confirmation for SIGTERM and reviewed messages. Bracketed paste enters only the composer text path. Small viewports cannot confirm hidden actions. Drafts survive report refreshes without following selection; results distinguish accepted signals/queues from confirmed exit or delivery. General provider/plugin registration remains excluded. See [usage](usage.md#process-actions) for the public contract and [feasibility research](research/session-actions.md) for provider evidence.

## Agent attribution adapters

Implemented on 2026-10-15. Built-in `CodexAttributionAdapter` and `ClaudeAttributionAdapter` conform to the internal [AgentAttributionAdapter contract](../Sources/AgentMonitorCore/AttributionAdapters/AgentAttributionAdapter.swift) and are registered by [AttributionAdapters](../Sources/AgentMonitorCore/AttributionAdapters/AttributionAdapters.swift). They live inside `AgentMonitorCore`; they have no OS access, UI dependencies or messaging responsibilities. The internal protocol is a source-code extension boundary, not a public third-party plugin API.

| Owner | Contract |
|---|---|
| Provider adapter | Declare provider identity, recognized executable shapes and accepted invocation names, allowlisted environment keys, required runtime observations and an optional session-listing command. Validate/normalize session markers, decode runtime evidence and listings, supply an exact detached-runtime link, and interpret shared-runtime evidence. |
| `ProcessArguments` | Decode the bounded argument/environment buffer, retain only the registry's allowlisted keys, and delegate marker interpretation. A malformed marker from any adapter rejects the marker set; a valid other provider cannot hide it. |
| `NativeProcessReader` | Perform same-user process inspection and PID/start/executable checks before and after metadata reads. Collect only the requested open-file paths or listening-socket paths; never read their contents. |
| Registry | Collect all recognition claims, restrict each adapter to its declared inputs, and reject duplicate provider registrations and markers carrying another adapter's provider. Fixed built-in registration contains one typed adapter per provider. |
| `Monitor` | Own CPU/footprint accounting, process-lifetime history, runtime boundaries, nearest-runtime marker selection, conflict resolution, detached matching and listed-session bindings per runtime lifetime. Require one live match that predates the marker-bearing process. |
| `MonitoringSession` | Decide when a listing is due and run it through the bounded provider-command runner; a failed or slow listing leaves runtimes unresolved. |
| Presentation | Consume resolved provider/session evidence and the core's shared-runtime classification. Own labels, sorting, filters and grouping; never recognize providers from executable paths or environment keys. |

An adapter's `runtimeObservations` declares `openFilePaths` or `listeningSockets`. Its `runtimeEvidence` decodes those observations into writer-thread IDs and listener paths without deciding process ownership. `runtimeLink` supplies either an exact writer-thread ID or an exact listening-socket path; the shared monitor compares that link against candidate metadata and enforces lifetime and uniqueness constraints. Codex requests file paths and decodes UUID writer-lock names; Claude requests listeners and links its validated inbox marker. No adapter receives the full environment, and the Claude adapter never declares or reads the messaging token.

Provider registration rejects duplicate providers. Runtime recognition is a set of claims, not a first-match lookup. Multiple adapters recognizing the same runtime establish a runtime boundary but leave provider and thread ambiguous, even when a descendant has a marker or a single writer candidate. Registration order cannot select a winner. A detached candidate must have exactly the marker's provider claim; conflicting candidates cannot supply a runtime. Nested providers retain both markers until the nearest unambiguous runtime selects the relevant provider. Missing, malformed and conflicting evidence remain distinct.

`ProcessSample.runtimeProvider` delegates to the built-in registry for the unique recognized provider. `Monitor`, native metadata enrichment and marker parsing use that same registry in production; internal injection permits tests to demonstrate the complete path with a synthetic adapter. `HeavyProcess.isSharedRuntime` checks the runtime lifetime and delegates evidence interpretation to the registered built-in provider; presentation supplies only the wording. No provider-specific recognition switch belongs in the sampler, ancestry resolver or UI.

### Harness session registries

Implemented on 2026-10-16. An adapter may declare a `SessionRegistryQuery`: a harness CLI command, run through `PATH` with declared environment overrides, that lists live runtimes and their sessions. The adapter parses the output into `RuntimeSession` values (runtime PID, normalized session ID, active flag); the host runs the command, binds sessions to runtime lifetimes and never lets the adapter perform I/O. Claude declares `claude agents --json` with nonessential network traffic disabled; Codex declares none. Codex registry integration is deferred because the inspected listings lack a verifiable native process relation; the [accepted assessment](proposals/codex-session-registry.md) records consequences and conditions for reconsideration.

- **Binding:** a live runtime binds only when exactly one listed entry names its PID, that entry is active and its session ID is a valid UUID. Several entries for one PID, as a multi-session server would list, leave it unbound. A binding belongs to one PID/start-time lifetime and is dropped with it, on an executable change or when the next listing no longer confirms it.
- **Evidence:** a process whose nearest runtime is bound, and which has no readable marker or single writer candidate, resolves to the bound session with `sessionRegistry` evidence. Markers and writer descriptors take precedence; malformed or conflicting metadata stays ambiguous. The evidence names the session the runtime hosts now, so a shell started before `/clear` or `/resume` can be shown under the newer session.
- **Cadence:** `MonitoringSession` lists a provider's sessions only when displayed findings include its `runtimeOnly` or `sessionRegistry` rows: immediately for a runtime the previous listing did not cover, otherwise at most once a minute so bindings follow `/clear`. Each listing has a 3-second timeout; failures clear that provider's bindings and wait for the same minute. One Claude listing measured about 0.3 s of CPU on 2026-10-16. A consumer can pause listings through the run loop's `resolveSessions` input while it shows no session identities, keeping existing bindings; the menu bar passes its open state, so closed-panel icon sampling never lists and the first open sample refreshes due bindings. The CLI and TUI omit the input and always resolve.
- **Consumers:** session grouping treats `sessionRegistry` as an exact session, and text reports call it the current rather than the launch session. Messaging does not accept it, because the inbox comes from the marker in the workload's own environment. Claude message verification reuses the same query and parser.

The menu bar app finds `claude` only when its `PATH` contains it, as with messaging; otherwise runtimes stay `runtimeOnly`.

### Harness adapters

Everything specific to one agent harness belongs to that harness's adapters; shared mechanisms stay in the host. Attribution lives in the core adapter described above, including the optional session registry. Messaging is a separate `AgentMessaging` action adapter per harness. Terminal focus is selected by terminal application, not by harness. A new harness such as OpenCode adds an `AgentProvider` case with an explicit JSON schema decision, an attribution adapter with exact positive and conflicting fixtures, and only the optional facets the harness supports. Process lifetimes, ancestry, conflict resolution, bounded commands and action verification remain shared.

The `AgentProvider` enum and marker types are unchanged by the adapter extraction. JSONL schema version 2 added the `sessionRegistry` evidence value. Messaging stays in the separate `AgentMessaging` capability and terminal focus in `TerminalFocusAdapter`; neither is required for attribution. Actions and sampling use the same attribution path, preserving recipient verification, process identity checks and launch-origin limitations described in [action contract](#process-and-session-actions).

Contract tests use a synthetic adapter to prove that custom recognition, declared marker keys, observation requests and detached-runtime evidence flow through the shared pipeline. They also cover duplicate registrations, overlapping recognition in both orders, malformed markers, built-in executable shapes and writer-path decoding. The existing attribution fixtures remain the behavioral oracle for nested agents, same-directory sessions, PID reuse, detached children and uncertainty. See [development guidance](development.md#changing-attribution-adapters).

## Deferred adapter capabilities

Optional session inspection and provider-specific metrics remain proposals; OS CPU/footprint measurements stay in the shared collector. Preserve typed values and units if inspection is added, and keep display strings in presentation. External plugins, dynamic loading and generic capability frameworks are excluded from the current implementation.

A third provider requires an explicit revision of the closed provider enum and JSON schema before it can participate. A future external adapter may use a versioned subprocess protocol with validated stable provider identifiers; its transport, discovery, installation and trust policy remain deferred until requested. The internal built-in interface does not promise binary or wire compatibility for third-party extensions.

## Resource history

[ReportHistory](../Sources/AgentMonitorPresentation/ReportHistory.swift) owns UI-independent scalar history from `MonitoringSnapshot.agentLoad`. It retains at most 3,601 one-second buckets, with per-metric peaks inside each bucket and a separate latest value. It never retains process identities or snapshots. Time-window projection produces right-closed peak buckets over the last 600 or 3,600 seconds (so 40 observations 15 seconds apart fill 40 distinct 10-minute bins), leaving empty/unavailable buckets unfilled. Snapshots without a summary leave the history unchanged; duplicate summary timestamps are ignored; a backwards wall-clock jump starts a new timeline. CPU/footprint require complete measurements within the observed summary; heavy count requires both resources complete. Table thresholds, grouping, sorting, pins and unrelated-process visibility never redefine the history population or heavy thresholds.

`LiveReportState` owns the collected history, selected metric/range and a frozen copy for paused inspection. Normal receipt records history before holding a paused snapshot; Resume reveals the intervening samples. Collection reset preserves history and choices while clearing paused inspection. The native host also records closed-panel samples after its collection-generation guard. History advances only on summary-bearing samples, with no timer, persistence or extra native/provider reads of its own. The sampler limits all-agent enrichment to the first delivered sample and then at most once every 15 seconds on an existing table sample (or the slower table cadence). A backwards wall-clock jump restarts this cadence. Between summaries, ordinary threshold-based enrichment and table delivery continue; `agentLoad == nil` means no summary was collected, not zero load or a collection error. The native icon derives its values independently from filtered findings at each displayed sample. Summary collection broadens metadata enrichment beyond heavy findings; collection-cost evidence belongs in research, not an assumed zero-cost claim.

The TUI spends one header line on the strip, including `h` metric and `t` time-range hints. Native presentation uses a 28-point strip inside the fixed-height scroll content, semantic grayscale bars over a persistent subtle baseline and the existing persistent AppKit options controller in a history-menu placement. That menu has checked metric/range choices and retains its items while tracking. Its title changes only outside tracking when the selected metric/range changes. The native current-value label says “No data” for an unavailable measurement, with explicit empty-history accessibility text; measured zero retains its numeric value. Both views scale bars from zero to the visible peak, at least 1; peak compression preserves short observed bursts without inventing measurements between samples.

TUI and native live tables default to a 5-second interval; text/JSONL default to one second. Explicit intervals override these defaults.

## Native menu bar app

Apple's interface guidance is the platform baseline; CodexBar is the primary visual reference for density, hierarchy and progressive disclosure, with RepoBar and Trimmy as secondary comparisons. The inline composer and action review justify the complex-content exception to Apple's preference for a menu. Keep system typography and semantic colors, and preserve shared core/action ownership. Reference observations and their limits are recorded in [native menu design research](research/native-menu-design.md).

`AgentMonitorMenuBar` hosts SwiftUI content in a transient, optionally detachable AppKit `NSPopover` anchored to a fixed-width `NSStatusItem`. It is an accessory app; `popoverShouldDetach` enables AppKit’s implicit detached window using the existing content controller. Closing that window uses the normal popover close lifecycle; there is no second collector or custom window implementation. Native disclosure rows, sorting, resource summaries and inline action review replace terminal cell layout. Disclosure headers are full-width buttons; details and action controls stay outside the toggle target. `MenuBarRowDisclosure` gives the native style an explicit group count or process kind. Only groups show a leading chevron; their trailing count badge and process info symbol share a minimum 40 × 32-point slot inside the row toggle. Counts can widen to preserve all digits. The separate pin button has a 32 × 32-point target. Child indentation is 24 points, and accessibility values distinguish showing processes from showing details. Counts still cover the group’s complete displayed heavy findings, including individually pinned members. An unpinned session with one displayed heavy process renders directly as a process row with project/session context; multiple displayed processes and explicitly pinned sessions retain a group header. Process summaries use two lines: process/PID and CPU above project/session and footprint, with clipped project names available in a tooltip and full attribution in details. This native projection does not change grouping identities, totals or the TUI hierarchy. The view consumes `LiveReportState` and `SessionGrouping`; direct row selection is a neutral presentation operation shared with keyboard navigation. No provider recognition or process collection lives in the view. Each native report render builds one neutral `ReportProjection` and reuses its groups for process/session labels and its pinned/unpinned rows for rendering; there is no persistent grouping cache.

Native initial focus is view-owned: `MenuBarInitialFocus` requests the first displayed row once per opening, or the table while empty/loading. `MenuBarFocus` distinguishes table, row header and pin control through one SwiftUI focus binding. The waiting transition targets the first arriving row only while that binding still identifies the table. Explicit navigation to another control cancels the request; later refreshes do not restore focus. The table focus target excludes options menus and the message editor. Initial assignment runs after the open view mounts; AppKit still owns the popover/window lifecycle.

Native row focus follows process/session identities; up/down traverses the native projection, including flattened singletons, while ←/→ collapses/expands the focused row without toggling on repeated presses. Disclosure and single-key shortcut gates inspect Command, Control, Option and Shift rather than requiring empty event flags: numeric-keypad flags on macOS arrows and Caps Lock state must not suppress those commands. Modified shortcuts remain ignored except Shift for `<`/`>` and the scoped bulk session command on Shift+←/→.

`MenuBarCollection` composes the native model's source with `MonitoringSession`; the app delegate and headless composition tests use that same wiring. Process reading, time and registry execution are injectable, with native production defaults. Each collection creates its reader at startup and forwards live thresholds, interval and session-resolution policy to the core.

The native panel keeps a user-chosen height through sampling, disclosure, pausing and action review. Compact, Standard (default) and Tall select 420, 560 and 720 points; width stays 420 points. The choice lasts until quit. On opening, the host caps the height to the current screen's visible height minus 40 points. Report or action content scrolls in the remaining space between fixed header and footer controls. Root geometry changes update the popover size, with unchanged sizes ignored. The hosting view retains intrinsic sizing and is fitted before assignment to avoid an initial zero-size popover. `MenuBarLayout` and `MenuBarPanelSize` own these dimensions; the same content size applies to the implicitly detached popover.

`LiveReportState` defaults to Stable order for native and terminal views. Process lifetimes and session identities have separate bounded rank maps: surviving identities keep their relative order, departed identities are removed, and new identities append. Initial and simultaneous arrival batches use descending CPU with deterministic identity tie-breaks. Switching to Stable order captures the current sort order; switching away enables the chosen resource/PID sort, and reverse is a no-op while stable. Pins remain above the ordinary list, without changing those ranks; stable children append within sessions, including pinned sessions. Pause reconciles only when its held sample is displayed, grouping switches preserve both rank maps, and native dismissal preserves ranks for reconciliation on reopening. No ordering state enters monitoring or JSONL.

Both native and terminal inspection reuse `LiveReportState.toggleFreeze`: Pause holds the displayed snapshot, including values, membership and automatic ordering, while collection retains only the latest pending sample. Resume applies that sample immediately. Explicit sorting and disclosure remain available; action services still verify live identities. Native Pause/Resume (`p`) is in the fixed header with the displayed sample's timestamp while paused; it is unavailable before a baseline or during action review. Reopening starts live. TUI `p` uses the same semantics, with the paused timestamp and resume key first in the header so narrow supported terminals retain them. There is no implicit hover pause.

`LiveReportState` owns ordered `ReportPin` identities and labels. Pins bind processes by PID plus start time, and groups by the existing provider/session or unresolved-process identity. `ReportProjection` resolves pins against the displayed snapshot, emits explicit unavailable placeholders, then the normally sorted remaining rows. Pins neither retain executable action state nor expand the sampling scope. Pin order survives sort/refresh/grouping changes; pinned group children use stable arrival order in Stable order, and PID/lifetime order in other sorts. Individually pinned children are removed from group child rows, and pinned groups own their members even in flat mode. Group totals remain derived from the complete heavy findings, not the projected rows. Missing pins cannot execute actions and remain until explicit unpin or quitting the monitor; returning exact identities restore live rows. TUI `.` toggles the selected pin, `p` pauses and `n` sorts by PID. Native live rows and unavailable placeholders share the same compact pin control, so sampling state cannot change its icon, size or action label. Native controls use a pin button, context menu and row-scoped `.` handler; Return and Space retain native control activation. Pin commands require the exact currently visible row and no open action panel, including explicit removal of unavailable pins. They never fall back to a stale selection or a hovered row. Keyboard pinning restores focus to the same identity after it moves between pinned/unpinned containers, when that identity remains visible.

Native row menus share Pin/Unpin, Focus terminal, Message and Terminate commands. Missing targets and action-ineligible rows retain disabled menu items. Groups permit only terminal focus when they resolve to one runtime; messaging and termination require a process row. Expanded buttons use the same eligibility checks. The action service exposes snapshot-only messaging/focus eligibility using the same prerequisites as execution, while fresh identity/recipient verification remains mandatory at execution. Menu opening performs no provider calls or native reads.

`MenuBarArrivals` compares process lifetime and session-group identities in successive displayed snapshots, independently of sorting, disclosure and pin containers. The initial snapshot establishes a baseline. Newly entering identities get individual monotonic three-second deadlines; unchanged identities retain their original deadline, departed identities are removed, and returning identities count as arrivals. Each new process also starts or renews its parent session header’s deadline, whether collapsed or expanded; the child retains its own deadline. A single cancellable task sleeps until the earliest expiry, with no recurring timer or process reads. Dismissal resets the baseline and cancels expiry; Pause delays arrival detection until the held sample is displayed on Resume. Only row headers receive the semantic grayscale background, avoiding stacked group/child shading. A short opacity fade is local to that background and disabled by Reduce Motion.

The native View options menu exposes the shared grouping, sort/direction, threshold and interval state, plus live-icon mode and a compact keyboard-help toggle. An AppKit pull-down button owns a persistent menu, populated at creation and refreshed through `NSMenuDelegate.menuNeedsUpdate` before opening. Snapshot-driven SwiftUI updates never mutate that control or its tracked menu items; delegate tracking callbacks only gate updates. Grouping and sort choices are flat checked items, and sampling submenus contain explicit values including the current value when outside the presets. Native interval presets reuse the shared TUI steps with an additional 15-second choice; direct setters update neutral presentation state and the running collector. Help renders inside the existing scroll area; it creates no window and does not resize the panel. The native source receives an async threshold reader and `LiveInterval`, like the TUI source; settings change the existing `MonitoringSession` without a collection restart. Native dismissal clears snapshots, pause, selection and executable action state while preserving pins, grouping, sort/direction, thresholds and interval in memory until quit. Live mode retains only the latest collected snapshot for immediate display on reopening; static mode resolves missing pins after a fresh baseline.

`MenuBarDelegate` routes right mouse-up and Control-left mouse-up to an AppKit context menu; ordinary activation retains the popover toggle. Opening the menu closes the popover through its existing draft-preserving lifecycle. `MenuBarStatusMenu` snapshots the current indicator text for that opening and reuses `MenuBarOptionsController` for checked options without the pull-down button’s title item. Background samples do not mutate the tracked menu. Open/Quit commands execute after menu tracking returns, avoiding a dismissal race with a newly opened popover. Status information does not rely on hover tooltips, and the menu adds no sampling timer or process reads.

`MenuBarModel` owns main-actor UI state and cancellable collection/action tasks. Live icon mode is the default: launch starts one `MonitoringSession` with a 250 ms first interval (or a shorter selected interval), then closed sampling uses 15 seconds, and opening switches the same collector to the user's panel interval through `LiveInterval`. The first delivered sample restores the normal interval on the same collector; subsequent open/close or static/live toggles do not repeat the startup burst. CPU averages the measured interval; opening does not invent a short-window sample from a long-window baseline. Dismissal clears report inspection/action state but keeps collection and the latest snapshot. Static icon mode cancels collection while closed and restarts from a fresh baseline on reopening. Cancelled tasks drain before a replacement collector runs; collection and action generations are separate so dismissal can invalidate actions without rejecting background samples. Quit cancels and drains both. No animation or independent polling timer drives the icon. Collection failure clears the live icon's measurements; opening retries collection. Cancellation cannot interrupt a synchronous native read already in progress. Physical app CPU/wakeups remain a measurement gate.

`MonitoringConfiguration.collectAgentLoad` opts into a UI-independent `AgentLoadSummary` on the [resource-history cadence](#resource-history). On those samples, the sampler enriches all observed same-user process lifetimes through the existing attribution adapters, then computes known agent-associated CPU and footprint totals separately from threshold-filtered findings. No second sampler or provider recognition path is introduced. Unrelated processes are excluded; shared runtimes count once and missing resource measurements remain explicit. Native and TUI collection enable this summary for the shared history strip; text/JSONL collection keeps it disabled and its flat output contract stays unchanged. Summary totals describe observed agent-associated processes, not guaranteed complete system usage or provider-reported working/idle state.

The native icon draws three thick template bars in a fixed 18 × 18-point image inside a square status item. A smaller monochrome numeric badge occupies the upper-left area above shortened bars, with a clear vertical gap at every count. Counts above 99 display 99+; the status menu and accessibility label preserve the exact count. Available filtered CPU is divided by logical processor capacity: zero fills none, below 25% fills one, 25% to below 50% fills two, and 50% or more fills three. The scale is fixed, never normalized to recent peaks. Both bars and badge derive from filtered `MonitoringSnapshot.findings`, using the displayed snapshot while open and the latest collected snapshot while closed. Pause holds both; Resume refreshes both immediately. The heading’s count covers the same distinct process lifetimes, including collapsed children and singletons but excluding missing pinned placeholders. Applied snapshot thresholds and sample time appear in status text. This projection adds no native reads and does not depend on the less frequent all-agent history summary. It reflects sustained load from the first successful sample and has no event history or expiry. A right-click status menu and accessibility label expose raw CPU (100% = one core), footprint, heavy-process count, sample time and missing-data qualifications. The same bar geometry remains at startup, on failure and in static mode. Missing CPU draws unfilled bars; the status menu explains availability, and an observed memory-heavy count can still appear. Startup and collection failure have no count, distinguishing them from measured zero. Static mode shows unfilled bars without a badge and disables closed-panel collection. The app inherits system appearance: SwiftUI/AppKit use semantic background, text and accent colors, and untinted template status images let AppKit choose contrast against the actual menu bar. There is no app-specific light/dark override or appearance polling. Never widen the status item or invert the bars as an event cue.

The panel reuses the existing action review state and `SessionActions` services. Confirmation targets a frozen process lifetime, and messages retain root-by-default routing, automatic workload context, exact-text review and live recipient verification. Closing cancels owned action work; quit awaits completion. A cancelled signal/send can have an uncertain outcome, which is retained for the next opening without automatic retry. Terminal focus can itself dismiss the transient panel. Live Automation behavior and provider delivery from the bundle are not established by fake-service tests.

Unsent message text survives automatic dismissal in memory until quit. A saved message retains the frozen process, original sample time and chosen recipient ID separately from the executable action panel. Resume uses the shared `beginMessage(for:)` preparation entry point, validates the original process/session through the action service, resolves the same recipient from fresh results and returns to composition; review and send are explicit again. Missing targets/recipients leave the text available to copy or discard. One saved message must be resumed or discarded before composing another. Explicit composer cancellation discards it; submitted or uncertain sends are never restored as unsent drafts.

The source-build script defaults to an optimized release build and assembles an ad-hoc-signed, unsandboxed local bundle with `LSUIElement` and an Automation usage description. Its run mode passes the invoking shell's PATH for existing provider transports. This is separate from CLI release packaging; signing identity, notarization, Finder/login PATH discovery, login items and production installation are deferred. App and TUI collectors are independent; there is no IPC or background service.

`ReportShortcut` defines shared TUI/native browsing keys and their neutral state transitions. Hosts keep interval wakeups and process actions local; ordinary sorting/history changes do not wake the collector. The native host blocks browsing shortcuts during all action phases, accepts unmodified browsing keys (plus Shift for angle brackets and scoped session disclosure), and routes row actions only through the exact visible focused identity. `.` is handled on row and pin buttons. Row headers handle ←/→ as explicit collapse/expand commands, and disclosure bindings honor that requested state rather than toggling; Return and Space retain native control activation. `y` and Copy PID write only the visible individual process’s numeric PID; groups, missing pins and reused/stale identities are rejected. Clipboard writers are injected in tests. AppKit menu tracking retains normal menu-key handling.
