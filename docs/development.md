# Development guidance

## Build and verify

For everyday CLI use, follow the [installation guide](installation.md). The commands here are for working on the source code.

For downloadable archives and GitHub publication, follow the [release guide](releasing.md).

### Choose checks for the change

Keep the POC loop lean: reuse the current backend, toolchain, SDK and Debug configuration, cap compilation at two jobs during interactive work, and batch related edits before validation. `swift test --filter` filters execution, not necessarily compilation. Build the current test executable once; use `--skip-build` only while it still includes all relevant edits. Package the tested Debug executable for local UI review with `AGENT_MONITOR_BUILD_CONFIGURATION=debug bash scripts/menubar.sh build`. The bundle script reuses the backend named by the current product link and defaults to two jobs; `AGENT_MONITOR_BUILD_SYSTEM` and `AGENT_MONITOR_BUILD_JOBS` explicitly override these choices. Keep optimized builds for performance or delivery checkpoints. Never accumulate two backend trees after a fallback.

`BaselineEvictionTests` compares eviction order and the conservative newborn floor against a full-sort oracle across seeded histories. Its churn guard bounds the number of sorted identities, and a long-missing lifetime fixture checks bounded lazy references without losing its retained counter endpoint. These are mechanism guards, not native cost measurements.

`DisplayCadenceTests` blocks the history sink on the publication worker while the production pipeline continues scanning, then checks exact CPU, endpoints, unit counts and timing coverage after backlog merging. `PublicationCoverageTests` checks memory/gap extrema, ordinary display aggregation without a backlog flag, and whole-unit history eviction. `SelfClockedAcquisitionTests` exercises the same synchronous deadline loop as the native clock, including interval changes, cancellation and overruns without catch-up scans. `AcquisitionHandoffTests` checks ring capacity, ordering and rejection without displacement. The native loop does not await actor admission; these guards do not establish OS scheduling guarantees.

Select checks by the behavior and artifacts affected, not by running every available probe. During implementation, use red/green tests for the changed behavior; before committing, run the affected suites and integration checks. For this POC, use focused regressions and affected integration checks even for bounded shared changes; reserve the full Swift suite for release gates, broad refactors or an explicit request. Repeat checks only after relevant edits, failures or unresolved concerns. Batch related edits before integration validation; a new commit alone is not a reason to repeat a full suite or optimized build. Use debug tests for red/green work. Build optimized products for a native integration, packaging, optimization-specific correctness or performance checkpoint, and run performance measurements against that optimized build. Always report the test configuration separately from the build configuration: a release build is not a release-mode test run. Save slow-command output once and inspect the same log. CI and release gates remain unchanged.

For a required full-suite run or a mixed native/PTY run, explicitly pass `--no-parallel`; `-j 2` limits compilation, not Swift Testing concurrency. On 2026-10-31 the full run without that flag hit PTY and acquisition/pipeline deadline failures; those failing cases passed in the explicit serial rerun. The two stale expectations found alongside them (the removed overview caption and the keyboard-menu shortcut suffix) were corrected. This does not establish a passing full serialized gate; [TEST-01](../PLAN.md#existing-validation-follow-ups) tracks that check.

Run selected commands from the repository directory:

```sh
bash scripts/doctor.sh
python3 scripts/docs.py check
swift test
swift format lint --strict --recursive Sources Tests Tools Package.swift
bash scripts/preview.sh check
swift build
python3 scripts/verify-poc.py "$(swift build --show-bin-path)/agent-monitor"

```

The Swift Testing suite covers attribution, ambiguity, PID reuse, nested runtimes, parsing, thresholds, native measurement, action identity/routing guards, offline message refusal and bounded subprocess behavior. Action integration tests signal only a disposable `sleep` child; PTY tests use an injected fake action service. No test should queue messages to live agents or signal user workloads. The smoke check compiles a disposable Swift fixture and launches controlled terminal process trees. It checks exact session IDs, same-directory sessions, detached workers, a scrubbed-marker fallback, CPU normalization, footprint, and exclusion of a small worker. An exited intermediate launcher leaves a marked worker under PID 1 while its Codex runtime keeps the thread writer descriptor open; the check requires the exact runtime and terminal context, independently of monitor history. It also verifies that a worker whose runtime exited retains only its marked session. It terminates only its own fixtures. Python 3 is needed for this development check, not for the monitor.

The [doctor](../scripts/doctor.sh) checks macOS, Swift, the active macOS SDK, Git, the canonical instruction symlink, and any installed project skills. It does not install dependencies or change configuration. Missing optional skills do not fail the check; an incomplete or modified installed skill setup does. It is a prerequisite check, not a replacement for building and testing.

### Supplemental inspection guards

The default-off [inspection feature](architecture.md#supplemental-inspection-observations) uses only fake readers/clocks for its acceptance guards. Run the `InspectionObservationTests`, `CarriedInspectionTests`, `InspectionSchedulingTests`, `InspectionConservationTests`, `NativeInspectionTests`, `InspectionPipelineTests` `InspectionInterfaceTests` and `TerminalCollectionTests` suites for targeted changes, and the full suite for shared accounting changes. `NativeInspectionTests` injects counter access; it performs no supplemental reads of real processes. Ordinary native reader tests remain part of the existing full suite, not evidence of inspection benefit.

The oracles check the last accepted cumulative counter across randomized disappearance/failure/reuse cases, complete-only output when inspection is disabled, historical-only carried memory/population, missing-scan intervals, reset exclusions, frozen inherited ownership, every native admission status, bounds, rotation, pause generations, deadline overruns and terminal discard counts. Mutations of census-success supersession, parent-start validation and census filtering must each fail their corresponding independent guard. No timing benchmark, real-provider call, owned-worker trial or live workload is authorized by these checks; native comparison needs a separate bounded approval.

`WorkloadCoverageTests` runs the production `MonitoringSession` with a synthetic clock and scheduled lifetimes, comparing baseline acquisition with experimental discovery. It separates exact identities read, admitted CPU, wholly unread lifetime CPU and final tails using independent synthetic end counters and successful-read times; overlap, PID reuse, executable changes and bursts above the discovery cap also check historical-only memory. Run `swift test --filter WorkloadCoverageTests`. Durations, arrival phases and uniform/front-loaded/end-loaded CPU are explicit assumptions, not a reconstruction of the [recordings](../Tools/WorkloadCapture/README.md); the cases establish accounting behavior, not native cost or real-workload loss percentages.

### Adaptive acquisition guards

[Adaptive acquisition](architecture.md#adaptive-acquisition) is implemented with default-off settings. Select the affected guards below and run the full suite for shared contract changes; all sources, clocks, registries and actions in these fixtures are injected.

- Core attribution and scheduling: `swift test --filter 'SamplingAttributionTests|AdaptiveAcquisitionTests|SamplingCoverageTests'` checks completed-negative invalidation, helper ancestry/PID reuse, production-controller agreement with the independent reference, startup and closed-context bounds, feature-plus-permission inspection overrides, due-deadline preservation and retained sampling diagnostics through coalescing/eviction.
- Production CPU conservation: `swift test --filter ProductionAdaptiveWorkloadTests` runs the actual controller and collection loop through idle agents, resumed work, a newborn burst and missing-read recovery. It checks exact sessions and scan spacing against the independent per-lifetime ledger and initial/unseen/unreadable/tail partition.
- Shared controls and wire/presentation: `swift test --filter 'AdaptiveSamplingOptionsTests|AdaptiveSamplingPresentationTests|SamplingCoveragePresentationTests'` checks explicit flag presence, validation/defaults, settings retention, valid interval steps, support-qualified rates and strict schema fields.
- Native controls and lifecycle: `swift test --filter AgentMonitorMenuBarTests` includes [sampling model guards](../Tests/AgentMonitorMenuBarTests/MenuBarSamplingTests.swift), menu validation/tracking and [offscreen sampling coverage](../Tests/AgentMonitorMenuBarTests/MenuBarAdaptiveCoverageTests.swift). These check live visibility forwarding without collection restart, paused settings changes and fresh static-mode reopening.
- Terminal adapter: `swift test --filter terminalAdaptiveIntervalKeysPreserveFullSourceSettingsWhilePaused` uses the owned PTY fixture to check full settings forwarding, adaptive-maximum wording, constrained interval keys while paused and terminal restoration. The fake source overwrites one test-owned settings file; ordinary fixture runs create none.

`swift test --filter AdaptiveSampling` also runs the retained test-only [reference controller](../Tests/AgentMonitorCoreTests/AdaptiveSamplingPrototype.swift), evidence model and focused synthetic workload guards. Keep the reference independent of production so the differential guard can detect policy drift. The research-only [scenario sweep](../Tests/AgentMonitorCoreTests/AdaptiveSamplingComparisonTests.swift) is excluded unless `AGENT_MONITOR_ADAPTIVE_COMPARISON=1` is set; its [reproduction procedure](../Tools/CPUAccountingProbe/README.md#adaptive-offline-comparison) saves one output log. It compares adaptive, fixed minimum and fixed maximum with a common virtual horizon, exact lifetime discovery, independent initial/unseen/unreadable/tail CPU, scan counts, requested-interval bands and override duty. Classification is injected; only supported markers are additionally checked through production attribution. Failed-listing recovery is reference-only because production drains accepted accounting and terminates on listing failure. [Retained results and limits](research/cpu-accounting.md#adaptive-sampling-offline-prototype--2026-10-27) describe model assumptions and phase-sensitive losses.

These checks use fake workloads/providers and do not establish native savings, live scheduling, actual idle-agent distributions, App Nap or physical menu/input delivery. User-run native smoke checks remain pending, and live diagnostic/cost/cadence measurements require a separate explicit request. Slower target defaults and persistent-unreadability relaxation remain unapproved under [ADAPT-01](../PLAN.md#resource-accounting-priority).

### Keep tests useful

Retire tests of removed UI components and prose or row-budget mirrors when a production interaction guard covers their requirement. Remove unused implementation with its tests rather than retaining dead code to satisfy fixtures. Update expectations when the public contract changes; do not delete a failing test that still exposes a current product defect.

Retain tests for distinct invariants and independently checkable failure classes. Remove repetition only after identifying which existing oracle and boundary still cover it; retain cold/warm, pre/post-pressure and whole-range eviction cases where they differ. Expensive production-composition, differential, allocated-capacity and lease-lifetime guards are not interchangeable with small unit tests. Inject an owned PID when a native test only checks that PID, preserving a separate enumeration guard. Gate a performance acceptance test on an explicit metric; measurement-only opt-in probes remain diagnostic tools, with their provenance and retained research links. Do not delete them merely because they are not ordinary regression tests.

Async progress guards must establish the blocked state before claiming independence: gate the next scan on consumer entry, or observe the internal waiter diagnostic before cancelling. Bound the readiness wait and release/join owned work on failure; an already buffered event or a task created immediately before cancellation does not establish concurrent progress or suspension.

A new oracle should fail for a representative wrong result. The production stall fixture checks per-session CPU and memory maxima in addition to global conservation, so transferring work between sessions cannot pass merely because the total is unchanged. Its smaller injected budget forces compaction, and its duration crosses the rolling-history boundary; production-population capacity has separate guards. The virtual clock acknowledges each published history unit so this fixture stalls delivery only, using the production pipeline and store. Separate blocked-publication and handoff-budget tests cover ingress pressure; do not let an instantaneous test clock accidentally combine those scenarios.

### On-demand workload recording

Follow the [recording and analysis playbook](../Tools/WorkloadCapture/README.md) for source/build provenance, fresh paths and explicit limits, footer/early-stop checks, and the offline analyzer. Start live recording only on explicit request; keep user recordings and provenance outside Git and do not delete originals automatically. Any retained research findings or dataset needs explicit authorization. `swift test --filter WorkloadCaptureTests` validates injected recorder behavior, file protection and failure handling; `python3 -m unittest discover -s scripts -p 'test_analyze_workload.py'` validates the file-only analyzer. These checks do not sample real workloads or establish complete exit accounting, final CPU, a process-wide heap ceiling or production monitoring cost. The recorder's `--help` and analyzer need no live collection; normal monitoring retains no automatic recorder state.

## Validation coverage

Resource changes must meet the [resource visibility requirements](architecture.md#resource-visibility-requirements). Validate attribution and accounting separately: a correctly attributed surviving process does not establish coverage of its exited siblings. Use disposable workloads with independently known CPU work and memory allocations, varying worker lifetimes across collection boundaries, below-threshold populations, nesting and PID reuse. Check for both missing work and double counting, distinguish current memory from historical observations, and preserve unknown ownership. Faster polling, lower thresholds or a larger reported total alone are not a success oracle. User-authorized read-only live captures can expose representative workload shapes, but do not replace controlled regression guards or establish a lossless total.

Each [GitHub release](https://github.com/mbackschat/agent-monitor/releases) records its own verification; the commands above and [terminal checks](#terminal-and-machine-output-checks) reproduce automated coverage. Retained live measurements and their environment limits are indexed in [research](research/README.md#retained-measurements); dated provider probes are recorded with their method in the relevant research notes. They do not establish compatibility with other systems or provider versions.

Heavy terminal Codex workloads and npm-based Claude installations remain unvalidated. The [bounded sustained observation](research/README.md#earlier-process-measurements) does not establish hours-long leak behavior, larger-population acceptance or sustained TUI behavior.

Keep terminal-focus test coverage at both boundaries: fake adapters for routing and a fake `osascript` for the production Terminal.app adapter. Never drive real terminals in automated tests.

Sampling can miss short-lived work. Live rates need consecutive valid observations; the [retained-counter contract](architecture.md#retained-counter-accounting) also recovers compatible CPU deltas across read gaps for wider windows, including eligible delayed first readings. Missing readable markers can leave detached processes unknown; launch-origin attribution does not establish which client caused a shared daemon's current load.

Terminal layout tests compare table padding, clipping and detail wrapping with the pinned SwiftTUI renderer's cell widths, including CJK, fullwidth names, emoji and combining marks. This verifies renderer geometry, not every terminal/font's Unicode display policy.

Retained accounting is guarded by `CounterLedgerTests`, `CPUAccountingTests`, `CPUDiagnosisWindowTests` and `NativeCounterOutcomeTests`, including failed reads, newborn baselines, PID reuse, counter resets, raw-tick precision, eviction, deduplication and recovery exclusions. Injected native calls verify failure classification, errno, identity and clock propagation without provider listings; an owned fixed-CPU child independently checks newborn accounting. `BaselineEvictionTests`, `PromptEvidenceTests` and `LifetimeOrderStorageTests` compare eviction/storage behavior with independent oracles, including allocated capacity under churn. These guards do not establish saturated acquisition cadence, complete churn/exit coverage, adapter continuity, native speedup or a process-wide heap ceiling.

Acquisition and display-window tests use controlled clocks and fake native readers to cover worker isolation, blocked consumers, deadline overruns, interval changes, bounded handoff, prompt-capture limits, deferred discovery, argument-read fallback, cancellation, coalescing, CPU conservation and partial-window failure. The owned 100 KiB environment fixture covers native fallback. Native composition checks local session evidence updates while the panel is closed. These checks establish separation and failure behavior, not saturated cadence, complete CPU coverage, interval-supported historical attribution or measured heap limits. The opt-in native sampling probe records process CPU and operation spans; overlapping spans include other threads and must not be added as isolated stage costs.

## README preview

The [preview script](../scripts/preview.sh) builds the development-only `monitor-preview` target. Its [synthetic ledger fixture](../Tools/Preview/LedgerFixture.swift) feeds the production `MonitoringSession`, recent-activity store, `LiveReportState` and `LiveReportLayout`; the [SVG generator](../Tools/Preview/Preview.swift) adds illustrative terminal decoration. It never samples processes or reads agent sessions. The fixture shares one synthetic clock across collection and metadata, supplies identity through synchronous launch capture, and acknowledges each report before advancing the next acquisition. Fixed identities, measurements, twelve one-second intervals and a 120 × 32 viewport make the rendered output reproducible without real-time sleeps.

```sh
bash scripts/preview.sh update
bash scripts/preview.sh check
```

`check` regenerates in memory and compares bytes; missing or different output fails with the update command and leaves the asset untouched. Run it when presentation, grouping, details, labels or fixture changes can affect the generated preview. `update` replaces [the SVG shown in README](assets/tui-preview.svg); if the preview changes, regenerate it, inspect spacing/clipping/legibility in an isolated headless browser, commit it alongside the change and rerun `check`. Edit [the generator and fixture](../Tools/Preview/), never the SVG by hand. Use synthetic identities and paths only, never live samples for documentation images. README embeds SVG directly, so there is no second PNG to synchronize and no converter or font package to install. Browser font appearance can vary; the asset's cell geometry and generated bytes are deterministic.

The generator places each visible grapheme at its terminal-cell coordinate and leaves spaces as gaps. Do not fit whole rows with SVG `textLength` or `lengthAdjust`: glyph scaling can distort the font, and collapsed whitespace can change the apparent column widths. Keep the fixed-cell regression tests and check the image in an isolated headless browser; a converter rendering alone does not establish browser compatibility. Use a fresh temporary profile, never an existing user browser or profile. Headless Chrome with `--disable-gpu --run-all-compositor-stages-before-draw` successfully rendered the published SVG during verification; GPU-backed capture was blank in this environment.

[CI](../.github/workflows/verify.yml) runs on every pull request, main push, and manual dispatch, avoiding path filters that could miss a new dependency. It runs the documentation checks, Swift suite, formatting, preview check, and offline skill-installer tests. The [Xcode 27 runner](https://github.com/actions/runner-images/blob/main/images/macos/xcode-27-arm64-Readme.md) supplies the required macOS SDK and Swift toolchain; the workflow selects Xcode 27.0 explicitly. No skill download is needed for CI. A stale preview fails the check; CI does not rewrite or commit assets. Requiring the check before merges is a separate repository branch-rule setting.

[Preview tests](../Tests/PreviewTests/PreviewTests.swift) exercise missing/stale asset detection, XML escaping, and process/session layouts at 60, 85, 120, and 160 columns. The ledger guard holds asynchronous metadata until the final report, checks first-interval session ownership and retained exited-worker history across all twelve intervals, and compares the final SVG with immediate metadata. This guarantees the rendered fixture contract, not identical internal metadata timestamps. The preview represents one illustrative state, not every interaction or exact terminal theme. Keep the existing layout and PTY tests, and review style-only TUI changes visually even if the SVG bytes do not change. `monitor-preview` is not part of the installed CLI or release archive.

The published SVG remained byte-identical. An earlier isolated stale check did not retain its differing output, so this reproduction does not establish that incident's exact cause.

Size documentation images for their displayed dimensions, allowing 2× resolution for raster icons. Keep optimized web assets rather than full-resolution masters, and check file size and visual quality before committing. The README logo is a 256 × 256 WebP displayed at 128 × 128; preserve explicit display dimensions and descriptive alternative text. ## Toolchain and package

The PoC uses Swift 6 language mode with complete concurrency checking, a Swift 6.4 package manifest, and a macOS 27 deployment target. It was built with Xcode 27 on Apple Silicon. The installed Apple toolchain is sufficient; no Homebrew installation is required. Swift 6.4.1 is available upstream, but this PoC does not require changing the Xcode toolchain. [Swift 6.4 release](https://www.swift.org/blog/swift-6.4-released/), [Swift 6.4.1 announcement](https://forums.swift.org/t/announcing-swift-6-4-1/90029).

`AgentMonitorCore` owns native inspection, process-lifetime history, attribution, and threshold filtering. `AgentMonitor` uses Apple's Argument Parser for typed options, generated help, and validation; the dependency is pinned to 1.8.2 in [Package.swift](../Package.swift). The migration passed the Swift suite, release build, help/error/JSON checks, and controlled attribution fixtures. Preserve the generated [Package.resolved](../Package.resolved). The monitoring core has no package dependencies. [Argument Parser release](https://github.com/apple/swift-argument-parser/releases/tag/1.8.2).

The completed [SwiftTUI evaluation](research/terminal-ui.md) used version 0.14.0 and synthetic data; its temporary package/build directory has been removed. The monitor now declares the same official remote dependency, exactly pinned in [Package.swift](../Package.swift). It compiles and runs through the public `RunLoop`, avoiding the scene launcher’s discovery socket. See the [evaluation findings](research/terminal-ui.md#libraries-inspected).

The mutable monitor is an exclusively owned value in one sequential sampling loop. Models are `Sendable`; there is no shared mutable singleton, unchecked sendability, or UI actor dependency. The native acquisition thread owns monotonic deadlines with explicit interval-change and cancellation wake-ups; async-only test clocks use the shared scan operation through a cancellable async adapter. Native pointers are confined to the reader and buffer parser. Preserve those boundaries if adding a UI or parallel collection.

Use four-space indentation and the bundled `swift format`, configured in [.swift-format](../.swift-format). Add behavior-focused Swift Testing tests before implementing changes. Native integration tests should use real API observations; attribution tests should use deterministic process lifetimes and explicit expected session IDs.

## Changing attribution adapters

Provider-specific attribution rules live in [AttributionAdapters](../Sources/AgentMonitorCore/AttributionAdapters/), under the internal `AgentAttributionAdapter` contract. Add executable recognition, allowlisted marker keys and validation, runtime evidence decoding and exact detached links there. The registry wires built-ins into parsing, native observation and resolution. The core owns OS calls, process identities, ancestry and conflict resolution; presentation consumes results. Terminal focus remains a separate action capability; messaging is unavailable. The [architecture contract](architecture.md#agent-attribution-adapters) defines these boundaries and the deferred extension scope.

For a provider change, demonstrate the declared inputs and exact session result with deterministic adapter/monitor tests. Retain negative guards for unrelated executable shapes, multi-call invocation names, duplicate marker values, malformed IDs, overlapping recognition claims in both orders, and duplicate provider registration. Exercise detached matches through the shared enrichment path so polling and action lookup stay consistent. Provider-listing and listed-name scaffolding is absent; never run a real harness listing in tests. A synthetic adapter must work through that path without adding branches to the sampler, parser, model or UI. Use disposable native fixtures to verify changes to descriptor decoding or the observations requested from the OS.

The host retains only declared environment keys and bounds native reads; adapters never receive full environment buffers or read transcripts. Never add the Claude messaging token to an allowlist. New observation kinds require a concrete provider need, a bounded host implementation and a regression test; they do not justify general plugin infrastructure. A third provider or wire-contract change needs an explicit enum/schema decision rather than silently expanding the existing API.

Treat a mismatch between code and documented ownership as part of the change being reviewed. Reconcile it within the authorized scope, or report a material scope conflict before extending the bypass. Keep [CLAUDE.md](../CLAUDE.md), [architecture](architecture.md), the user-facing support claims and [PLAN.md](../PLAN.md) current in the same commit. Do not report a boundary as implemented until production consumers use it and the contract tests pass.

## Skills shared by Codex CLI and Claude Code

The repository-owned [monitor-ui-ux skill](../skills/monitor-ui-ux/SKILL.md) is required for UI/UX advice, design, implementation and review in Mac or TUI. It is tracked with the project, uses the repository license and needs no download. Both discovery paths link to `skills/monitor-ui-ux`; read that canonical source directly if the host has not refreshed its skill catalog. Update its routing when the owning contracts move, and update the [review procedure](#resource-overview-ux-review) when accepted interaction requirements change. Skill validation and filesystem discovery do not establish that a fresh host has loaded it or that an interface is usable.

Upstream skills are optional development aids, not build/runtime dependencies. Use an installed skill when its documented task matches; if it is unavailable, follow the linked project contracts and state the limitation without blocking routine work. Install only for an explicit setup request or a task that actually needs the missing resource; do not install or upgrade merely because a symlink is absent. Do not install project skills globally. On a fresh clone, upstream skill links remain unresolved until `install` populates ignored `.skill-sources/` at the locked revisions; missing optional skills differ from a broken installed setup, which the doctor reports as an error.

**Every project skill must work with both hosts.** A canonical skill directory must include its `SKILL.md`, referenced resources, and license. Expose the same directory under both `.agents/skills/<name>` and `.claude/skills/<name>` through relative symlinks. Verify both paths resolve to the same file and that every relative reference exists. ## Build and probe artifact retention

`.build` is disposable working storage, not a project archive. Source, pinned dependencies (`Package.resolved`), maintained probe sources and indexed measurements in [research](research/README.md) are the durable inputs. Before deleting an experimental output that supports a retained claim, save its small sanitized result and interpretation in research; do not retain raw machine-wide traces merely because they are ignored by Git.

| Artifact | Retention rule |
| --- | --- |
| `.build/out`, module caches, manifests and dependency checkouts | Rebuildable. Keep the active tree during builds/tests; remove stale configurations and caches when idle. |
| Design-study images and supporting render files | Always reuse `.build/design-studies/`; review images are PNG files. Never track study images in Git or place them in `docs/assets/`. Keep written findings and decisions in indexed documentation. |
| Local `Agent Monitor.app` bundle | Rebuildable with the [menu bar build](#menu-bar-app). Keep the current app while it is being used; remove obsolete spike/duplicate bundles. |
| Probe executables, exported XML, Instruments `.trace` directories and release-verification downloads | Temporary. Delete after the required result has been extracted and retained; raw traces can grow by gigabytes in seconds. |
| Test/profile logs for the active change | Keep through validation/review, then retain only the evidence needed to explain the result. Tests can regenerate routine logs. |
| Measurements, decisions and review conclusions needed later | Store in their indexed documentation location, never solely under `.build`. |

Use [clean-build.py](../scripts/clean-build.py) for new probes and experimental exports. Its read-only `check` runs before and after the local menu-bar build and from `doctor.sh`: it fails on top-level logs older than seven days, PNGs outside `design-studies`, abandoned scratch runs and coexisting build-backend trees, even when Debug and Release each reference one of them. Findings require review, not automatic deletion; product links do not prove a tree is idle. This is a narrow guard for demonstrated waste, not a generic artifact classifier or cache-size limit. Completed-checkpoint logs should normally be removed sooner, after recording their findings.

```sh
python3 scripts/clean-build.py run -- bash -c 'your-probe > "$AGENT_MONITOR_SCRATCH/result.json"; your-analysis "$AGENT_MONITOR_SCRATCH/result.json"'
python3 scripts/clean-build.py check
python3 scripts/clean-build.py clean
python3 scripts/clean-build.py clean --apply
```

`run` creates a locked scratch directory and removes it on normal exit, command failure or Ctrl-C; commands must wait for their children. Interrupted cleanup signals only a still-running owned command's process group, with a five-second wait after SIGTERM and, if needed, SIGKILL. A vanished group still permits reaping the owned command. Termination failure preserves the original interruption as the primary exception and retains the cleanup failure as traceback context. The scratch directory is preserved because the command may still be running; its inherited lease continues protecting it from cleanup. Analyze output inside that command and copy only explicitly approved durable evidence out before it exits. Each run also prunes unlocked abandoned scratch directories older than seven days. `clean` is a dry run unless `--apply` is supplied; it only considers marked `run-*` directories under `.build/scratch`, skips active locks and symlinks, and never cleans SwiftPM products, caches, app bundles or arbitrary `.build` files. A forced kill can leave a scratch directory for the next cleanup. Validate the script with `python3 -m unittest discover -s scripts -p test_clean_build.py`; its mocked interruption guards cover signaling/reaping failures, already-finished commands, disappearing groups and bounded escalation without signaling user workloads.

Check size before and after profiling with `du -h -d 2 .build`. Keep one active build backend; do not create a new scratch tree for each retry. Never clean an active compiler/test tree. A full `.build` removal is appropriate when idle if all durable evidence is already retained; the next build restores dependencies and products.

### User-first presentation

Design around the user's decision, not the internal data model. The user's 2026-10-30 review established these acceptance rules for Mac and TUI:

- **High priority: be concise in Mac and TUI.** Author each tooltip or contextual hint for one immediate purpose, normally within 75 characters including any available shortcut. Use one short phrase, not paragraphs, implementation explanations or instructions repeated from neighbouring controls. Do not shorten by blindly truncating text or hiding essential uncertainty. Put fuller definitions in Help & glossary, deeper evidence in labelled disclosures and full paths/arguments in selectable Details. In TUI, keep labels, status lines and keyboard help brief and use its existing scrollable detail/reference pages for explanations. Audit shared help strings and inherited ancestor help as well as local literals; a short control label can still inherit a large tooltip. Review default and hover text separately.
- **Lead with what matters.** Before adding a field or control, state what it helps the user understand or do. At a glance, users should find the responsible agent/session, workload, resource use and any limitation that changes how they interpret it. Do not give implementation metadata the same visual weight.
- **Use progressive disclosure.** The default view shows the useful summary. Details adds context and comparisons; deeper attribution evidence, identifiers and diagnostic mechanics are available on demand. Do not hide the primary answer behind disclosure, and do not expose every available field merely because it exists. Material missing measurements remain visible.
- **Explain at the point of use.** Use plain labels with clear units and populations. Give unfamiliar terms, counts and meaningful symbols concise native tooltips and accessible descriptions. Help & glossary supplies fuller definitions; it must not be required to decipher an ordinary row. Brief help is a tooltip, not a new click-open panel with a Close button. Follow Apple's [help-button convention](https://developer.apple.com/design/human-interface-guidelines/buttons): use one standard SwiftUI [HelpLink](https://developer.apple.com/documentation/swiftui/helplink) in the footer to open Help & glossary. Contextual information-circle buttons open relevant content; never use a help or information control symbol as an inert tooltip target. Put brief native tooltips on the relevant label or control, using [Apple's tooltip guidance](https://developer.apple.com/design/human-interface-guidelines/offering-help); longer definitions belong in the glossary or a labelled disclosure. Status badges within buttons and uncertainty symbols describe state, not independent actions.
- **Choose a visual form that answers the question.** Details must add information beyond the row; do not repeat its chart at a larger size or retain extra measurements solely to populate a chart. Use charts for history and patterns, aligned tables for comparisons, and familiar SF Symbols for compact cues. Use spacing, typography, contrast and restrained color to make importance and grouping apparent. Prefer readable values and meaningful graphics over diagnostic sentences or raw field dumps; visual polish is part of correctness.
- **Make the next step clear.** Warnings explain the user-visible effect and offer a relevant route when one exists. Symbols and actions stay beside their subject. Adding a shortcut or another access path must preserve existing visible controls unless their replacement or removal was explicitly requested. Before changing a control cluster, list its accepted entry points; after the change, compare the complete rendered cluster against that list, not just the new or repaired control. Treat successive requests as cumulative unless the user explicitly supersedes an earlier requirement. Avoid technical shorthand such as “same-user PIDs” or “interval averages” in persistent overview chrome when it does not help the user decide what to do.
- **Review the user's experience, not the existence of code.** Check the default view, expanded detail, narrow layout, light/dark appearance and missing-data cases. Ask what attracts attention first, what can be removed, whether the important answer is apparent without Help, and whether secondary information is explained and reachable. Verify actual hover/click behavior separately; a `.help` modifier or passing render test is not proof of responsive live help.

### Cross-interface issue review

A screenshot identifies where a defect was noticed, not its product scope. For every report, check Mac, TUI, text CLI and JSON before closing it. Record affected, unaffected or not applicable for each, with the shared model/renderer/input path that settles the classification. Check the behaviour and meaning, not just matching strings: current row membership versus process existence, exact identities and paths, counts and resource totals, missing values versus zero, filters, history range, and action availability. Preserve machine-readable fields and units when shortening human-facing wording. Native hover, focus, resizing and SF Symbols need terminal-appropriate equivalents only where the same task exists; do not add terminal hover or JSON presentation markup. Run focused guards for affected outputs. Earlier fixes in the same session must be included when this review was previously omitted; put unresolved counterparts in PLAN rather than declaring a Mac fix complete product-wide.

### Shared information and diagnostics

- Keep the main agent/session/CWD/executable comparison visually dominant. Move detailed collection diagnostics and explanations into a clearly named on-demand view; retain a concise, actionable indication of material missing measurements beside affected totals.
- Give every metric a clear population, unit and time range. A process-count column must say that it counts processes; “Now” alone is insufficient. Distinguish latest-sample presence from recent history and confirmed termination, and do not present overlapping counts as additive categories. Tooltips supplement labels rather than repair their meaning.
- Define separate behavior for selection, expanding children, inspecting details and actions. Put a control beside its target or give a clearly labeled selected-item inspector. Column-header help describes the column, never a hidden selected-row target. Keep executable and directory distinctions readable when narrow; do not rely on color or hover to establish ownership.
