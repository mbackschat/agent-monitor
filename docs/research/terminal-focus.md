# Focusing the terminal that hosts a session

Checked 2026-10-14 on macOS 27.0.1 (build 26A434). Question: can a TUI key bring the terminal window, tab, and split pane hosting the selected row's agent runtime to the front, given the runtime PID, its start time, its controlling terminal device (for example `ttys015`), and its full ancestry? Feasibility only; nothing was implemented. Every claim cites a source URL or a local command. Rows and paragraphs are tagged **Doc** (documented or upstream source), **Local** (observed here), or **Inference** (reasoned, not verified).

Local checks were read-only: listing `/Applications` and `~/Applications`, `sdef` on installed apps, `plutil`/`PlistBuddy` reads of `Info.plist`, `--help` of installed CLIs, `man tmux`, SDK header reads, `ps` ancestry of this shell, environment variable *names* (`env | cut -d= -f1`), and `defaults read -g AppleSpacesSwitchOnActivate`. No AppleScript, `osascript`, `open`, terminal CLI command, activation, selection, or input was run. No permission was granted or changed.

Implementation status (2026-10-15): the adapter boundary, the Terminal.app adapter and the app-only fallback are implemented; see [architecture](../architecture.md#process-and-session-actions). The prototype gate below is still open. First manual use (2026-10-15) found that Terminal's `windows` also lists a window without tabs (class `item`); reading its tabs fails with -1728, which aborted the whole search for every session in a later window. The adapter now skips such windows, verified read-only against the live window list; afterwards the user confirmed that focus selected the session's tab. Background, minimized, other-Space and full-screen cases remain unrecorded.

## Verdict

Feasible with exact tab (and pane where the terminal has them) fidelity for terminals that let an outside process match a session by TTY: Terminal.app and iTerm2 via Apple Events with no user setup beyond one Automation consent, WezTerm via its CLI, kitty only after the user enables a remote-control socket, and Ghostty only from the unreleased 1.4 line. A tmux layer can resolve the pane and the outer client terminal, then hand off to those adapters. VS Code, Cursor, JetBrains IDEs, Zed, Warp, and Alacritty offer no outside interface to select a specific terminal tab; only activating the application is safe there. Two uncertainties block a firm promise: whether macOS 14+ cooperative activation honors activation triggered from a command-line process on macOS 27, and how Spaces and full-screen windows behave. Both need a manual prototype gate before the feature is claimed.

## 1. Identifying the hosting terminal

The runtime's controlling terminal is the join key: every scriptable terminal below reports a per-session TTY path, and a live runtime holding that pseudo-terminal keeps the device from being assigned to another tab (**Inference** from pty allocation semantics). Compare device numbers (`stat(...).st_rdev` against the runtime's `e_tdev` from `proc_bsdinfo`) rather than strings, because apps report forms such as `/dev/ttys016` ([Ghostty sdef](https://github.com/ghostty-org/ghostty/blob/main/macos/Ghostty.sdef), [iTerm2 scripting docs](https://iterm2.com/documentation-scripting.html)) while `ps` prints `ttys019`.

**Detection order (Inference, recommended).** First revalidate the runtime (PID plus start time) and read its current controlling terminal; without one, focusing is unavailable. If the runtime's ancestry reaches a tmux server or its environment carries `TMUX`, resolve the pane and its attached client first (section 2), then continue with the client process and the client's TTY as the new subject. Walk the subject's ancestry to the first process whose executable is inside an application bundle and for which `NSRunningApplication(processIdentifier:)` exists; that is the host app candidate. If ancestry ends at `launchd` (iTermServer after restart, detached mux servers), use allowlisted markers (`__CFBundleIdentifier`, `TERM_PROGRAM`, `ITERM_SESSION_ID`, `WEZTERM_UNIX_SOCKET`, `KITTY_LISTEN_ON`, `TMUX`) read through the existing `KERN_PROCARGS2` allowlist only as candidates. A candidate counts as the host only after that terminal's own enumeration reports a session with the same TTY. Markers are inherited at launch and can be stale (for example after tmux reattachment from another terminal), so a marker alone may justify app activation, never tab selection. Environment reads can be incomplete ([terminal-process observations](terminal-process-observations.md)).

## 3. macOS permission and activation model

**Automation (Apple Events).** TCC attributes a command-line tool's requests to its *responsible code*: "Run by the user from Terminal — The tool's responsible code is Terminal"; the algorithm "is not documented, has changed in the past". — **Doc** [Quinn, Apple DTS](https://developer.apple.com/forums/thread/756510). Consequences (**Inference**): the prompt names the terminal hosting Agent Monitor as the controller and the target terminal as the controlled app; the monitor binary cannot supply its own `NSAppleEventsUsageDescription` (documented as required for apps that send Apple events: [Apple](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription)); and a grant applies to everything run in that hosting terminal, including dictionary commands such as Terminal's `do script` or reading tab `contents`. Spawning `osascript` does not change the attribution. Whether Terminal.app controlling Terminal.app (monitor and agent in the same app) prompts at all is untested. `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)` lets the TUI show "needs permission" without triggering a prompt (**Local** SDK header).

**Accessibility.** `AXRaise`/`kAXMainAttribute` can raise one specific window of any app, but require the responsible app (again the hosting terminal) to be a trusted accessibility client, a far broader grant. AX enumeration also hides windows: AppKit filters `kAXWindows` to the current Space ([AltTab windowserver notes at `ab1bda4`](https://github.com/lwouis/alt-tab-macos/blob/ab1bda4769d3ada5f20b3a4b6c304b975fcf61da/src/windowserver/README.md), which resorts to private `_AXUIElementCreateWithRemoteToken` enumeration), and full-screen windows are missing from `kAXWindowsAttribute` ([developer forum report](https://developer.apple.com/forums/thread/121114)). Not recommended for this feature.

**Activation.** From macOS 14, "app activation is driven by user intent. It is treated by the system as a request and is not always guaranteed to be honored"; `activateIgnoringOtherApps` is deprecated; cooperative activation "guarantees successful activation as long as the yielding app is active at the time of the request". — **Doc** [AppKit release notes for macOS 14](https://developer.apple.com/documentation/macos-release-notes/appkit-release-notes-for-macos-14), [`activate(from:options:)`](https://developer.apple.com/documentation/appkit/nsrunningapplication/activate(from:options:)), [`yieldActivation(to:)`](https://developer.apple.com/documentation/appkit/nsapplication/yieldactivation(to:)). The monitor is a command-line process inside the active terminal, not itself an active `NSApplication`, so it cannot yield (**Inference**). Candidate routes, all untested here: an Apple Event `activate` sent to the target (the target activates itself); `NSRunningApplication(processIdentifier:).activate(options:)`; `NSWorkspace.openApplication` with `OpenConfiguration.activates` (default true, "brings it to the foreground": [Apple](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/activates)). The user's keypress is real intent, but which route macOS 27 honors from a CLI must be observed manually.

**Spaces, full screen, minimized.** With "When switching to an application, switch to a Space with open windows for the application" enabled (Apple default: [Desktop & Dock settings](https://support.apple.com/guide/mac-help/mchlp1119/mac); **Local** value `1`), activation moves to *a* Space with that app's windows; whether it follows the window just ordered front is unverified. Full-screen windows are their own Spaces. Terminal.app's `miniaturized` is writable, so a minimized target can be restored; other terminals' handling is unknown.

## 4. Generic fallback

When the host app is identified but no adapter can confirm the TTY, the only safe fallback is activating that application by PID and reporting "brought <App> to front; could not select the session". Activation may surface a different window of the same app than the one hosting the session. Matching AX window titles is rejected as a default: titles are set by shells and programs, are not unique, omit other-Space and full-screen windows, and need Accessibility. A wrong-window focus silently misleads the user into acting in another session, which is worse than an honest partial result.

## 5. Safety

- Use a per-adapter allowlist of operations: read TTY/ID properties, select tab/session/pane, order or un-minimize a window, activate the app. Never send `do script`, `write text`, `input text`, `send key`, `kitten @ send-text`, `wezterm cli send-text`, `tmux send-keys`, or read screen `contents`/`history`/`text`, although the same consent would permit them.
- Address the running process by PID (an Apple Event target by process ID; the matching socket for CLIs). A bare `tell application "Name"` launches a non-running app, which iTerm2's own `it2` code guards against ([`CookieAuth.swift`](https://github.com/gnachman/iTerm2/blob/master/it2cli/Sources/it2core/Auth/CookieAuth.swift)), and name lookup can hit a second instance.
- Revalidate the runtime's PID and start time and its current TTY immediately before acting; refuse on mismatch. Do not focus based on a launch marker alone.
- Pass TTY and IDs as typed Apple Event parameters or argument arrays, never interpolated script text; validate device paths against `/dev/ttys[0-9]+`.
- Bound every Apple Event and CLI call with a short timeout off the UI path; a consent prompt or a hung target must not freeze the TUI. Do not retry automatically.
- Expected side effects: the monitor's own terminal loses focus; if monitor and agent share a window, selecting the agent's tab hides the monitor; tmux selection changes what other attached clients see. Surface these in the action's description.
- Running external CLIs (`wezterm`, `kitten`, `tmux`) executes user-installed binaries; resolve them from the identified app bundle or an absolute path, not `PATH` alone (**Inference**).

## Recommended minimal design

1. **First: Terminal.app and iTerm2** through in-process Apple Events targeted by PID, matching TTY by device number, with tab (Terminal) and pane (iTerm2) fidelity. They need no configuration beyond one Automation consent and together cover the installed and most common macOS terminals.
2. **Always: app-only fallback** for every recognised GUI host (Ghostty 1.3, WezTerm without a socket, kitty without remote control, Warp, Alacritty, VS Code, Cursor, JetBrains, Zed), labeled as partial.
3. **Second: tmux resolution** in front of the terminal adapters, offered only when exactly one client shows the session or the user chooses a client.
4. **Later: WezTerm, kitty, Ghostty 1.4** adapters once installed and tested; WezTerm still needs a window-raise step, kitty needs user setup, Ghostty needs a stable release.

Place execution in `AgentMonitorActions` and run identification only when the key is pressed; sampling stays free of Apple Events and terminal CLIs. Return a neutral outcome (`focusedPane`, `focusedTab`, `activatedAppOnly`, `needsPermission`, `permissionDenied`, `needsTerminalSetup`, `sessionNotFound`, `unsupportedHost`, `runtimeChanged`) for presentation to render.

**Permission UX.** Before the first use, check with `AEDeterminePermissionToAutomateTarget(askUserIfNeeded: false)` and show "requires Automation permission" in the action panel. The first explicit keypress explains that macOS will ask whether the *hosting terminal* may control the target terminal, and that the grant applies to all programs run in the hosting terminal; then the system prompt appears. On denial, point to System Settings › Privacy & Security › Automation. Never request Accessibility.

**Prototype gate before claiming support.** Manually, with disposable tabs: Terminal.app tab in a background window, minimized window, another Space, a full-screen window, and the monitor and target in the same window; record which activation route macOS 27 honors from the CLI. Automated tests use fake adapters only and never drive real terminals.

## Gaps

- Activation from a command-line process under macOS 27 cooperative activation is unverified for all three candidate routes.
- Spaces, full-screen, Stage Manager, and multi-display behavior after selection are unverified.
- Whether Terminal.app prompts for consent when the controller is Terminal.app itself, and how the prompt reads given its missing usage string, is untested.
- iTerm2, Ghostty, WezTerm, kitty, Alacritty, Warp, Cursor, and zellij are not installed; their rows rely on documentation and source at the cited revisions. iTerm2's AppleScript deprecation trajectory and tmux `-CC` integration are unexamined.
