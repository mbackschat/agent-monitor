# Focusing the terminal that hosts a session

Checked 2026-10-14 on macOS 27.0.1 (build 26A434). Question: can a TUI key bring the terminal window, tab, and split pane hosting the selected row's agent runtime to the front, given the runtime PID, its start time, its controlling terminal device (for example `ttys015`), and its full ancestry? The initial investigation was read-only; the later manual observation is identified separately. Current behavior belongs in [architecture](../architecture.md#process-and-session-actions). Every claim cites a source URL or a local command. Rows and paragraphs are tagged **Doc** (documented or upstream source), **Local** (observed here), or **Inference** (reasoned, not verified).

Local checks were read-only: listing `/Applications` and `~/Applications`, `sdef` on installed apps, `plutil`/`PlistBuddy` reads of `Info.plist`, `--help` of installed CLIs, `man tmux`, SDK header reads, `ps` ancestry of this shell, environment variable *names* (`env | cut -d= -f1`), and `defaults read -g AppleSpacesSwitchOnActivate`. No AppleScript, `osascript`, `open`, terminal CLI command, activation, selection, or input was run. No permission was granted or changed.

## Observed feasibility and limits

Source interfaces expose TTY-based tab/session lookup for Terminal.app and iTerm2, CLI control for WezTerm, and configured-socket control for kitty. Inspected Ghostty 1.4 source added identifiers absent from 1.3. No external terminal-tab selection interface was found in the inspected editor CLIs/dictionaries. These findings do not establish universal absence of such interfaces or successful activation on every desktop configuration.

A follow-up on 2026-10-15 found a Terminal.app `windows` entry of class `item` without tabs; reading its tabs failed with -1728 and prevented searching later windows. A read-only window-list check confirmed the shape, and after the adapter skipped it the user confirmed selection of the session's tab. Background, minimized, other-Space, full-screen and first-consent behavior remain unrecorded. The remaining [manual checks](../development.md#manual-terminal-focus-check) are tracked outside research.

## Local observations

- **Local** Installed hosts: Terminal.app 2.15, Visual Studio Code 1.140.0, Zed 1.23.3, IntelliJ IDEA 2026.1.4 and Android Studio 2026.1 (in `~/Applications`), tmux 3.8, and `/usr/bin/screen`. iTerm2, Ghostty, WezTerm, kitty, Alacritty, Warp, Cursor, and zellij are not installed, so their rows rest on documentation and source only.
- **Local** This shell's ancestry: `Terminal` (PPID 1, no TTY) → `login` → `-zsh` → `claude` on `ttys019` → tool `zsh` with no TTY. The terminal application is a direct ancestor here, and agent tool subprocesses can lack a controlling terminal, so the workload's TTY can be absent even when its runtime has a terminal. — `ps -o pid,ppid,tty,comm` walk.
- **Local** Environment names present in this Terminal.app-hosted shell: `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `TERM_SESSION_ID`, `__CFBundleIdentifier`; absent: `ITERM_SESSION_ID`, `KITTY_*`, `WEZTERM_*`, `TMUX*`, `ZELLIJ*`. Values were not read.
- **Local** Terminal.app dictionary (`sdef /System/Applications/Utilities/Terminal.app`): `tab` has read-only `tty`, `processes`, `busy`, `contents`, `history`, and writable `selected`; `window` has writable `index` ("ordered front to back"), `frontmost`, `miniaturized`, `visible`, plus `selected tab`. There is no pane class. The Terminal Suite also contains `do script`.
- **Local** `sdef` returns error -192 (no scripting dictionary) for Visual Studio Code, Zed, IntelliJ IDEA, and Android Studio. `code --help` and `zed --help` expose opening files, folders, and windows, but no option that selects an integrated terminal.
- **Local** Terminal.app's `Info.plist` has no `NSAppleEventsUsageDescription`; VS Code's and Zed's contain a generic "An application in … wants to use AppleScript." — `plutil -extract`.
- **Local** `defaults read -g AppleSpacesSwitchOnActivate` returns `1` on this machine.
- **Local** SDK headers (Xcode SDK) provide `AEDeterminePermissionToAutomateTarget(…, askUserIfNeeded)` returning `errAEEventWouldRequireUserConsent` (-1744) when consent would be needed and not requested, plus the `kAEDoNotPromptForUserConsent` send mode (`AppleEvents.h`); `AXIsProcessTrustedWithOptions` with `kAXTrustedCheckOptionPrompt` (`AXUIElement.h`); `kAXRaiseAction` (no discussion text) and writable `kAXMainAttribute` (`AXActionConstants.h`, `AXAttributeConstants.h`).
- **Local** `man tmux` (3.8): formats `pane_tty`, `pane_pid`, `client_tty`, `client_pid`, `client_session`; `switch-client -c target-client -t` where "-t may refer to a pane … to change session, window and pane"; pane IDs are "passed to the child process of the pane in the TMUX_PANE environment variable"; tmux "initialises the TMUX variable with some internal information".

## 1. Identifying the hosting terminal

The runtime's controlling terminal is the join key: every scriptable terminal below reports a per-session TTY path, and a live runtime holding that pseudo-terminal keeps the device from being assigned to another tab (**Inference** from pty allocation semantics). Device numbers (`stat(...).st_rdev` and `e_tdev` in `proc_bsdinfo`) offer a potential normalized comparison: apps report forms such as `/dev/ttys016` ([Ghostty sdef](https://github.com/ghostty-org/ghostty/blob/main/macos/Ghostty.sdef), [iTerm2 scripting docs](https://iterm2.com/documentation-scripting.html)) while `ps` prints `ttys019`.

## 3. macOS permission and activation model

**Automation (Apple Events).** TCC attributes a command-line tool's requests to its *responsible code*: "Run by the user from Terminal — The tool's responsible code is Terminal"; the algorithm "is not documented, has changed in the past". — **Doc** [Quinn, Apple DTS](https://developer.apple.com/forums/thread/756510). Consequences (**Inference**): the prompt names the terminal hosting Agent Monitor as the controller and the target terminal as the controlled app; the monitor binary cannot supply its own `NSAppleEventsUsageDescription` (documented as required for apps that send Apple events: [Apple](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription)); and a grant applies to everything run in that hosting terminal, including dictionary commands such as Terminal's `do script` or reading tab `contents`. Spawning `osascript` does not change the attribution. Whether Terminal.app controlling Terminal.app (monitor and agent in the same app) prompts at all is untested. `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)` lets the TUI show "needs permission" without triggering a prompt (**Local** SDK header).

**Accessibility.** `AXRaise`/`kAXMainAttribute` can raise one specific window of any app, but require the responsible app (again the hosting terminal) to be a trusted accessibility client, a far broader grant. AX enumeration also hides windows: AppKit filters `kAXWindows` to the current Space ([AltTab windowserver notes at `ab1bda4`](https://github.com/lwouis/alt-tab-macos/blob/ab1bda4769d3ada5f20b3a4b6c304b975fcf61da/src/windowserver/README.md), which resorts to private `_AXUIElementCreateWithRemoteToken` enumeration), and full-screen windows are missing from `kAXWindowsAttribute` ([developer forum report](https://developer.apple.com/forums/thread/121114)). No Accessibility-based implementation was tested here.

**Activation.** From macOS 14, "app activation is driven by user intent. It is treated by the system as a request and is not always guaranteed to be honored"; `activateIgnoringOtherApps` is deprecated; cooperative activation "guarantees successful activation as long as the yielding app is active at the time of the request". — **Doc** [AppKit release notes for macOS 14](https://developer.apple.com/documentation/macos-release-notes/appkit-release-notes-for-macos-14), [`activate(from:options:)`](https://developer.apple.com/documentation/appkit/nsrunningapplication/activate(from:options:)), [`yieldActivation(to:)`](https://developer.apple.com/documentation/appkit/nsapplication/yieldactivation(to:)). The monitor is a command-line process inside the active terminal, not itself an active `NSApplication`, so it cannot yield (**Inference**). Routes untested in the initial source review: an Apple Event `activate` sent to the target (the target activates itself); `NSRunningApplication(processIdentifier:).activate(options:)`; `NSWorkspace.openApplication` with `OpenConfiguration.activates` (default true, "brings it to the foreground": [Apple](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/activates)). The later tab-selection confirmation does not establish behavior across all of these routes.

**Spaces, full screen, minimized.** With "When switching to an application, switch to a Space with open windows for the application" enabled (Apple default: [Desktop & Dock settings](https://support.apple.com/guide/mac-help/mchlp1119/mac); **Local** value `1`), activation moves to *a* Space with that app's windows; whether it follows the window just ordered front is unverified. Full-screen windows are their own Spaces. Terminal.app's `miniaturized` is writable, so a minimized target can be restored; other terminals' handling is unknown.

## App activation versus session selection

Activating a known GUI application does not establish which of its windows or tabs becomes visible. Window titles are mutable and non-unique; the Accessibility enumeration limits above further weaken title matching as session evidence. The current focus contract and operation allowlist belong in [architecture](../architecture.md#process-and-session-actions).

A bare AppleScript application name can launch an absent app. iTerm2's own [cookie helper](https://github.com/gnachman/iTerm2/blob/master/it2cli/Sources/it2core/Auth/CookieAuth.swift) checks for a running app before addressing it. Resolving an external CLI also introduces executable-discovery behavior separate from finding the terminal's session.

## Gaps

- The single Terminal.app tab-selection confirmation does not establish activation across all three candidate routes or desktop states.
- Spaces, full-screen, Stage Manager, and multi-display behavior after selection are unverified.
- Whether Terminal.app prompts for consent when the controller is Terminal.app itself, and how the prompt reads given its missing usage string, is untested.
- iTerm2, Ghostty, WezTerm, kitty, Alacritty, Warp, Cursor, and zellij are not installed; their rows rely on documentation and source at the cited revisions. iTerm2's AppleScript deprecation trajectory and tmux `-CC` integration are unexamined.
- Ghostty 1.4 is not released as of this check; its AppleScript API is a preview.
- zellij session targeting from outside and `screen` support were not established.
- The exact TTY string format returned by each terminal was not observed locally; the device-number comparison above remains untested across hosts.
