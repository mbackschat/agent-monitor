# Evaluate existing cores before building attribution

**Evaluate agent-top and tidewake against terminal-based Codex workloads before committing to a new collector.** Codex CLI is the first attribution target; terminal-based Claude Code follows later. Direct alternatives already address coding-agent resource attribution: agent-top offers a separate Rust core for both providers, tidewake supplies explicit evidence rules for detached processes, and claude-top demonstrates a native Swift collector worth studying for its reusable mechanisms and later Claude support. They provide stronger starting points than generic system monitors. The principal opportunity is trustworthy ownership: distinguishing a known agent launch from a same-directory guess or a shared service. This assessment recommends comparing those mechanisms against a controlled workload before selecting a language or adopting code. The [product document](PRODUCT.md) separates confirmed requirements from recommendations and excludes desktop-agent variants from initial scope. ([agent-top core](https://github.com/kannandreams/agent-top/blob/5961bf0087d9f827bc4963a8d00c3780000a3ad1/crates/agent-top-core/README.md), [claude-top](https://github.com/mbrummerstedt/claude-top), [tidewake classifier](https://github.com/berkkorkmaz/tidewake/blob/7dcb8d83a5b9c5e869c3b39ba75c2fc12d1f7076/internal/attrib/attrib.go))

## Existing tools make adoption a real option

The clarified goal is selective: surface the heavy consumers among dozens of processes and identify their **specific agent sessions**. Agent labels and project grouping alone fail when several sessions share a directory. Candidate evaluation should therefore prioritize filtering and exact session evidence; smaller processes matter only when needed to explain ancestry. A broad process dashboard is not the requested product.

Agent-top is the strongest headless reuse candidate because `agent-top-core` already separates discovery and attribution from its terminal presentation. It handles Codex and Claude, reports process/session join methods, and distinguishes logical subagents from OS processes. Its limitations matter: some associations use working-directory and timing heuristics, and previously unseen orphan ancestry cannot be reconstructed from a current process tree. Its JSON output makes it suitable for evaluating whether an existing application already solves enough of the problem. ([Core contract](https://github.com/kannandreams/agent-top/blob/5961bf0087d9f827bc4963a8d00c3780000a3ad1/crates/agent-top-core/README.md))

Claude-top is the closest native architecture reference, with Swift targets, CLI/JSON output, and menu bar presentation. Its inspected attribution is Claude-specific and starts with a messaging-socket marker, whose availability is narrower than its broad README description suggests. Corral adds a useful native collector example with start-time-aware caches. Tidewake is especially valuable for its distinction between explicit markers, ancestry, path evidence, and uncertainty; its macOS collector shells out to system tools, so suitability for frequent sampling remains unmeasured. ([Claude attribution](https://github.com/mbrummerstedt/claude-top/blob/d088212b58ad7a9b8d424ca283e4aef90224227e/Sources/ClaudeTopKit/AttributionEngine.swift), [Corral scanner](https://github.com/popyapp/corral/blob/39ba7680fb18f79b9f824274d8446e8e18d16c8b/Sources/Corral/ProcessScanner.swift), [Tidewake collector](https://github.com/berkkorkmaz/tidewake/blob/7dcb8d83a5b9c5e869c3b39ba75c2fc12d1f7076/internal/proc/collect_darwin.go))

**Keep Swift and Rust open until that comparison.** Swift offers direct C interoperability and a straightforward eventual native UI; Rust offers a reusable attribution core now. Optional future UI alone should not outweigh demonstrated headless correctness. If agent-top-core satisfies the difficult cases, retaining it can justify a later interface boundary. If it requires substantial replacement, a small Swift collector borrowing reviewed native patterns becomes more attractive. Generic libraries such as sysinfo help with sampling but do not supply agent ownership; its `session_id()` is an OS session, and its memory accessor reports RSS. ([Swift interoperability](https://www.swift.org/documentation/cxx-interop/), [sysinfo API](https://docs.rs/sysinfo/latest/sysinfo/struct.Process.html))

The leading candidates have inspected MIT license files, making selective reuse worth evaluating. This is not a completed dependency audit: pin the adopted revision, retain required notices, and inspect copied-file provenance and dependencies. The [solutions inventory](existing-solutions.md) records license evidence, source links, maintenance observations, and additional references including Stats, bottom, macmon, psutil, and ProcessMonitor.

## Reliable blame requires more than a process tree

Ancestry is useful evidence while parent and child coexist. After a parent exits, macOS ordinarily reparents surviving children to PID 1; a later snapshot loses that original edge. Retaining previously observed ancestry helps, but polling cannot recover an intermediate parent that existed entirely between scans. Darwin kqueue does not fix this generally: its fork event does not deliver the child PID, and automatic child tracking is unsupported. ([Apple exit semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/_exit.2.html), [Darwin event definitions](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/event.h))

The installed Codex reports **0.162.1**. Matching release source injects `CODEX_THREAD_ID` for the active logical thread and `CODEX_SESSION_ID` for its shared root thread into shell-command environments. Neither is an OS process identity: resumed conversations and logical subagents require separate runtime PID/start identity. This makes passive child-marker attribution a concrete first experiment, although these variables remain implementation-backed signals rather than established stable external APIs. A root executable need not carry its active thread in its own initial environment. The [Codex terminal note](codex-terminal-attribution.md) records pinned source and proposes an open writer-lock descriptor fallback for idle roots; that fallback is untested. ([Thread injection](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/protocol/src/shell_environment.rs#L81), [root identity](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/agent/control.rs#L85))

For later Claude support, prefer documented `CLAUDE_CODE_SESSION_ID` over the conditional messaging socket, retaining MCP resume/session-change caveats. The providers need separate semantics over a shared process identity model. ([Claude environment reference](https://code.claude.com/docs/en/env-vars))

The [local probe](terminal-process-observations.md) found three native terminal Codex roots but no live children to validate their session markers. A controlled Python child retained readable synthetic markers after reparenting; `/bin/sleep` returned argument data without its injected markers despite syscall success. Thus marker absence cannot establish non-agent origin. These observations support feasibility and identify an inspection limit; they do not establish end-to-end terminal attribution or explain the omission mechanism.

Both agents document hooks carrying session and tool context, but the reviewed schemas do not supply a general child OS PID. Codex app-server documentation shows nullable `osPid` fields; the pinned 0.162.1 core background-terminal record lacks them, so populated values cannot be promised. Its protocol process handle is not a kernel PID. Nor does app-server establish an attachable endpoint for every running CLI. These interfaces need versioned adapters and capability checks. ([Claude hooks](https://code.claude.com/docs/en/hooks), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [pinned background record](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/codex_thread.rs#L215), [app-server documentation](https://learn.chatgpt.com/docs/app-server))

Recommend keeping cheap process-lifetime/parent/counter history broadly, filtering heavy consumers, then selectively enriching those consumers and their ancestors. Join readable thread/root markers to the recorded runtime, and show the specific session with terminal/project context and its evidence. Preserve detached associations and explicit gaps. A shared daemon's launching session does not prove ownership of its later requests. Exact tool-call attribution and source-code profiling remain separate from this session-mapping contract. See the [proposed mapping](codex-terminal-attribution.md).

## Define the threshold before trusting its number

Recommend interval CPU usage, with **100% meaning one occupied CPU**: `100 × Δ(userCPU + systemCPU) / Δelapsed`. A first sample has no delta and should remain unavailable. CPU and elapsed counters must share a timebase; inspected Darwin resource accounting uses Mach time values, so treating every raw value as nanoseconds is unsafe. PID plus sufficiently precise process start identity should guard sampling and caches against PID reuse. ([Apple resource structures](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/resource.h), [resource population](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/bsd_kern.c), [process metadata](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h))

Recommend explicitly labeled **physical footprint** as the primary memory signal, with RSS available separately. Footprint accounts for compressed memory and other ledger components that RSS alone does not capture. The illustrative 1 GB threshold still needs a decimal/binary decision; neither this nor the CPU normalization is an approved requirement. Session totals should count each process once and describe summed footprint as aggregate process accounting, not exact unique physical RAM or guaranteed reclaimable memory. ([Apple task ledger](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c))

Normal-user libproc collection is a feasible starting point, with permission failures and disappearing processes represented explicitly. It is not a guarantee of access to every process or field. Conventional Endpoint Security brings restricted entitlement and deployment requirements; it should be considered only if simpler evidence cannot satisfy the attribution contract. The newer descendants-only API is an interesting future launcher option, but its limited subtree visibility does not solve discovery of arbitrary existing sessions. See the [platform note](macos-process-attribution.md) for SDK/version and permission qualifications. ([Apple access checks](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c), [Endpoint Security entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.endpoint-security.client))

## Choose skills around the current work

If Swift is selected, recommend **AvdLee Swift Concurrency and Swift Testing** first. Their inspected guidance addresses cancellation, isolation, asynchronous tests, and deterministic behavior—immediate concerns for a collector. Add one SwiftUI skill and Dimillian's SwiftPM app-packaging skill only when a GUI or distribution task exists. These are source-reviewed recommendations, not measured skill rankings, and none supplies verified Darwin attribution logic. ([Concurrency skill](https://github.com/AvdLee/Swift-Concurrency-Agent-Skill), [Testing skill](https://github.com/AvdLee/Swift-Testing-Agent-Skill), [packaging skill](https://github.com/Dimillian/Skills/tree/main/macos-spm-app-packaging))

Portable `SKILL.md` instructions can serve both Codex and Claude Code, but hook configuration, agent behavior, and MCP tooling are host-specific. Preserve references and licenses and verify loading in each installed CLI. Axiom offers broad Apple-development guidance with explicit host differences; use selected material initially. MobileBuildMCP, renamed from XcodeBuildMCP, is executable build tooling rather than just instructions, and is unnecessary until an Xcode workflow justifies it. ## Let controlled evidence settle the remaining choice

The next decision needs a controlled comparison. Recommend candidate trials with two terminal Codex sessions in the same directory, a busy grandchild, a detached child, and a shared service. A launch ledger supplies expected ownership. **Positive cases with readable markers or recorded lineage must resolve the exact session**, including distinct sessions in one directory; returning unknown everywhere cannot pass. Ambiguity cases must avoid false assignment. Measure attribution coverage among heavy consumers separately from correctness, without inventing a target before measurement. Repeat provider cases for Claude Code later.

Compare resource measurements under steady CPU work and controlled memory allocation, aligning definitions and sampling windows. PID reuse and exit races need fixtures; collector overhead needs measurement at an agreed interval. These are proposed acceptance oracles, not completed experiments. The small synthetic observations above do not substitute for those trials.

If an existing tool passes the user's actual attribution cases, adoption or a narrow extension is preferable to maintaining another collector. If none does, the comparison identifies a concrete missing guarantee to build. The [working model](agent-working-model.md) assigns HIGH to those contracts and hard correctness questions, MEDIUM to bounded research and implementation, and LOW to mechanically verifiable evidence work, without activating future delegation. No language, dependency, skill installation, or monitoring architecture has been selected by this research.
