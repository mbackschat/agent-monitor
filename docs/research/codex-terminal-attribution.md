# Codex process and session identity findings

The initial investigation checked sources and the local installation on 2026-10-14 for Codex CLI 0.162.1, focusing on local terminal CLI execution. The separately dated [session-listing follow-up](#session-listing-investigation--2026-10-16) checks 0.163.0 and distinguishes source evidence about other hosts from live coverage. The implemented attribution contract belongs in [architecture](../architecture.md#agent-attribution-adapters); this note records provider evidence and its limits.

## What the installed version actually provides

A read-only local check resolved `/opt/homebrew/bin/codex` to `/opt/homebrew/Caskroom/codex/0.162.1/bin/codex`; `codex --version` returned `codex-cli 0.162.1`. The version command also reported that creating PATH aliases was denied. No upgrade, configuration change, agent conversation, or environment dump was performed. The executable is locally installed; its full source tree was not available at that installation path.

The official GitHub release tag `rust-v0.162.1` resolves through annotated tag `7a078f6bb4ce0dc2a81408b334ce52979d92c603` to commit **`092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`**, dated October 9, 2026. All source links below pin that commit. This matches the reported version, not a separately verified bit-for-bit build identity. [Tag reference](https://api.github.com/repos/openai/codex/git/ref/tags/rust-v0.162.1), [annotated tag](https://api.github.com/repos/openai/codex/git/tags/7a078f6bb4ce0dc2a81408b334ce52979d92c603).

Unified exec injects the current thread and root-session IDs while constructing its command environment; user-entered shell commands also call these injection functions. Therefore a process marked as Codex-originated is not necessarily a command chosen autonomously by the model. Provider events can distinguish `UserShell` from other command sources. [Unified execution](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/unified_exec/process_manager.rs#L1382), [user-shell execution](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/tasks/user_shell.rs#L159).

The generic session model maintains logical threads in a shared map of `ThreadId` to `Arc<CodexThread>`. Subagents are therefore not required to have distinct native Codex processes. The logical agent graph therefore differs from the OS process tree. [Thread manager](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/thread_manager.rs#L417).

The official npm launcher locates and spawns a platform binary with inherited stdio. A Node wrapper is therefore a distinct launch shape from the observed native installation, not evidence that every Node process is Codex. [Pinned launcher](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-cli/bin/codex.js#L226).

## Runtime evidence and metadata

**Child markers.** The markers are injected into child command environments. The top-level executable's initial environment need not contain its current thread ID. This follows from construction of a separate environment map for each shell launch. [Environment injection](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/exec_env.rs).

**Writer descriptors.** Version 0.162.1 creates per-thread writer locks under `<codex_home>/thread-writer-locks/<thread_id>.lock` and holds their file handles. An open descriptor supplies version-specific runtime/thread evidence without reading conversations. File existence alone is insufficient: stale files exist and upstream cleans them by checking locks. A runtime can hold several thread writers. The implemented adapter and conflict rules are documented in architecture; this source review alone did not validate retrieval from a real terminal workload. [Writer-lock implementation](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/rollout/src/writer_lock.rs#L15).

**Session metadata.** The pinned `SessionMeta` includes thread ID, root-session ID, parent-thread ID, cwd, source, and CLI version. The source distinguishes rollout IDs after revert from stable thread IDs, so a filename UUID alone does not establish thread identity. [Metadata and history identity](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/protocol/src/protocol.rs#L2912).

If there is no readable marker, no historical launch edge, and no verified runtime association, the original session may be unrecoverable. Project and command matches are non-unique. This limitation particularly affects descendants detached before monitoring began.

## Exact command attribution is a separate problem

Official hooks document session, working-directory, and tool-call context, but do not promise a general child PID field. A hook's own PID is not the shell command's PID. The reviewed hook fields include session/cwd, tool input and `tool_use_id`; subagent events identify their parent session and agent separately. Timestamp/command matching cannot establish a unique child when concurrent calls overlap. [Official hooks contract](https://learn.chatgpt.com/docs/hooks).

App-server background-terminal listing is also insufficient as the sole process oracle. Official documentation shows nullable `osPid`, CPU, and RSS values; the pinned core `BackgroundTerminalInfo` contains only item ID, protocol process ID, command, and cwd. The documented nullable fields do not establish populated kernel IDs in that release, nor an attachable endpoint for every independent CLI. [Core record](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/core/src/codex_thread.rs#L215), [official app-server documentation](https://learn.chatgpt.com/docs/app-server).

## Limits of the evidence

Source inspection establishes where labels originate, not their readability from every process. The [local probes](terminal-process-observations.md) found readable markers on a synthetic orphaned Python child but not on a marked `/bin/sleep` child despite syscall success. A missing marker therefore does not establish non-agent origin. Current live coverage is recorded in the [development guide](../development.md#validation-coverage).

Logical thread/root identity is separate from a PID/start identity, cwd, terminal device or tool-call ID. A shared daemon's launch session does not identify the client responsible for its later load. When no marker, captured ancestry or runtime association survives, the originating session may be unrecoverable; matching directory or command text is not unique evidence.

The reviewed hook schemas do not establish a universal hook-to-child-PID mapping. No source finding here establishes compatibility with desktop-hosted tools, remote workloads or every independently launched Codex server. Claude's marker and lifecycle semantics are recorded separately in [Claude session findings](claude-session-messaging.md#session-markers-and-hooks).

## Session listing investigation — 2026-10-16

### Version and method

This follow-up answers the [ATTR-02 brief](../proposals/codex-session-registry-research.md) for **Codex CLI 0.163.0** on macOS 27.0.1; it does not revalidate every 0.162.1 finding above. `/opt/homebrew/bin/codex` resolved to `/opt/homebrew/Caskroom/codex/0.163.0/bin/codex`, whose SHA-256 was `8813367285524ac798dd96d1b071aea30d58708c7226fd236cd275cf1cfdee31`. Release tag `rust-v0.163.0` resolves through annotated tag `129b8ec7ee6f4511557a4856279f529025c25af4` (2026-10-15) to **`83086188ae0614bd882818ff1aa23f3194962012`**. Source links in this section pin that commit; matching the version does not prove reproducible binary equivalence. [Release reference](https://api.github.com/repos/openai/codex/git/ref/tags/rust-v0.163.0), [annotated tag](https://api.github.com/repos/openai/codex/git/tags/129b8ec7ee6f4511557a4856279f529025c25af4).

The investigation inspected CLI help, generated the installed binary's experimental JSON Schema into a temporary directory, read the pinned official source and made one successful listing connection to the existing default local app-server. A temporary Python client used `codex app-server proxy`, an RFC 6455 handshake, `initialize` with `experimentalApi: true`, `initialized`, `thread/loaded/list`, and one `thread/backgroundTerminals/list` per loaded thread. It followed pagination, imposed a 15-second deadline and opted out of all notification methods enumerated by the generated schema. Only anonymous counts, response field names and timings were retained. No transcript/history method, thread start/resume, turn, message or termination request was sent, and no disposable session was created. Two earlier attempts failed at socket connection with sandbox `Operation not permitted`, before initialization; the successful attempt used approved expanded permissions.

### Endpoint and host coverage

The proxy connects to one Unix socket, by default `<codex_home>/app-server-control/app-server-control.sock`; `--sock` can select another. Its source relays bytes and has no daemon-start fallback. The app-server transport match starts a Unix acceptor only for a Unix-socket transport; stdio starts a stdio connection instead. Consequently, discovering one shared daemon does not discover every independent app-server using the same Codex home. ### Cost and side effects

The [retained anonymous measurement](codex-session-listing-2026-10-16.json) contains the single successful run: ten loaded threads, one background terminal across those threads, zero populated OS PIDs, zero received notifications and a clean proxy exit. End-to-end wall time was **61.277 ms**, including proxy launch, handshake, initialization, eleven listing RPCs and cleanup. The loaded-list RPC took **2.743 ms**; the ten terminal-list RPCs took **0.155–1.770 ms** each. `wait4` measured **10.067 ms user + 12.731 ms system CPU for the proxy only**. Server CPU, Python-client CPU and network activity were not measured. Cleanup polled process exit at 10 ms intervals, so the wall result includes that measurement overhead. This is neither a warm-call distribution nor an amortized sampling-cost claim.

The following side effects are distinguished from live observations:

- **Local writes, source-established:** CLI dispatch prepares temporary aliases below `<codex_home>/tmp/arg0-macos`, creates/locks a per-invocation directory and performs stale-directory cleanup. Even `--help` and `--version` emitted alias-write warnings in the restricted environment. The successful proxy call emitted no warning; filesystem writes were not traced. A listing command is therefore not literally filesystem-write-free. [Alias setup](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/arg0/src/lib.rs#L331).
- **Shared server state, source-established:** initialization records connection capabilities and, for ordinary client names including the probe's `agent_monitor_research`, can update process-global client identity/user-agent metadata and initialize automatic gateway-login policy. It also calls analytics `track_initialize`. The two internal client-name exceptions are an implementation detail, not a documented observer capability. The probe did not set `explicitGatewayOauth`, whose true value would change shared login policy. No authentication prompt was observed, but this does not establish absence of every initialization effect. [Initialization](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/initialize_processor.rs#L132).
- **Network, source-established possibility:** proxy transport itself is local Unix I/O. Server initialization can enqueue analytics, whose delivery depends on the existing server's configuration. The documented `[analytics] enabled = false` suppresses analytics/metrics; it is not a universal nonessential-traffic switch. Passing a config override to the byte-relay proxy does not reconfigure that running server. No config was changed, and no absence-of-network claim follows from this probe. [Analytics queue gate](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/analytics/src/client.rs#L314), [initialize tracking](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/analytics/src/client.rs#L402), [documented metrics control](https://learn.chatgpt.com/docs/config-file/config-advanced#metrics).
- **Session execution, source-established:** the two listing handlers inspect existing in-memory state and do not submit turns, resume threads or subscribe the connection to thread history. The probe requested no session mutation and received no notifications. This is narrower than proving that establishing the connection has no effect on an active server.

Two additional live timing probes were requested but rejected by automatic approval review because repeated initialization can alter shared metadata and emit analytics. They were not executed. The retained evidence is deliberately a single successful sample; further initialization-based live experiments need explicit approval in light of those effects.

### Unresolved empirical questions

- Total server CPU, network traffic, logging and filesystem effects attributable to a listing connection amid concurrent work; the single probe does not isolate these costs.
- Live visibility across independent exec, embedded TUI, IDE and desktop servers, and whether each supported host offers an attachable observer endpoint.
- Whether a later version populates OS PIDs with process-lifetime and local-host semantics, or offers a non-originating observer handshake without shared metadata changes.
