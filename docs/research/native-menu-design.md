# Native menu bar interface references

Observed 2026-10-15. Apple guidance was read on that date; upstream repositories were inspected at the revisions below. Screenshots are repository examples, not proof of current runtime behavior, dimensions or accessibility. No upstream app was executed and no source or image was vendored.

## Apple guidance

| Source | Finding |
| --- | --- |
| [The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar) | Prefer a menu for a menu bar extra; a popover is an exception for functionality too complex for a menu. Use a recognizable template icon or symbol. Extras can be hidden by the system, so their position and continued visibility are not guaranteed. |
| [Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers) | Keep the surface focused on a few related tasks and size it to its contents. Avoid stacked popovers. | [Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls) | Disclose secondary details while keeping essential information visible. A disclosure triangle expresses a hierarchy. The restriction on multiple disclosure buttons concerns the push-style control, not every triangle in an outline. |
| [DisclosureGroupStyle](https://developer.apple.com/documentation/swiftui/disclosuregroupstyle) | Apple's custom-style example wraps the label in a button and gives it a rectangular content shape. This supports a larger click target than the triangle alone. |
| [Labels](https://developer.apple.com/design/human-interface-guidelines/labels), [typography](https://developer.apple.com/design/human-interface-guidelines/typography), [accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) | Prefer system typography, concise labels and semantic text colors. macOS text-size guidance differs from touch platforms; compactness still requires legibility, sufficient contrast and accessible controls. |
| [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos), [layout](https://developer.apple.com/design/human-interface-guidelines/layout) | Comfortable density, alignment and limited navigation depth suit precise pointing. ## Content sizing API observations — 2026-10-15

Apple's [NSPopover.contentSize](https://developer.apple.com/documentation/appkit/nspopover/contentsize) documentation says the initial content size matches the content view when its controller is assigned. [NSHostingController.sizingOptions](https://developer.apple.com/documentation/swiftui/nshostingcontroller/sizingoptions) controls generated sizing constraints; Apple notes that fewer options reduce layout measurements when the host can make size assumptions. The [preferred-content-size option](https://developer.apple.com/documentation/swiftui/nshostingsizingoptions/preferredcontentsize) concerns the ideal size and requires hosting-controller constraints; it does not apply directly to `NSHostingView`. [Size-based scroll bounce](https://developer.apple.com/documentation/swiftui/scrollbouncebehavior/basedonsize) applies only when content exceeds the viewport.

The subsequent [sizing experiment](development-tools.md#content-sizing-application--2026-10-15) distinguishes source guidance from observed offscreen behavior. The original fixed-height and draft-loss observations above describe the pre-change implementation; current accepted behavior is in [architecture](../architecture.md#native-menu-bar-app).

## Built-in popover detachment — 2026-10-15

Apple’s [`popoverShouldDetach(_:)` documentation](https://developer.apple.com/documentation/appkit/nspopoverdelegate/popovershoulddetach(_:)) states that returning true without a custom detachable window lets AppKit reuse the popover’s content controller. It also states that closing the detached popover delivers the normal close callbacks. Source inspection found the host already used an NSPopover delegate and explicitly returned false. Inference: enabling implicit detachment preserves the current content and close lifecycle without a second window implementation. Physical dragging, closing and reopening have not been exercised through computer control.

## Standalone SwiftUI table expansion — 2026-10-27

The earlier application-specific SwiftUI table attempt was recorded as failing to restore nested initially expanded descendants, including offscreen branches. A subsequent web review found no exact independent report or Apple acknowledgment. Apple's [DisclosureTableRow documentation](https://developer.apple.com/documentation/swiftui/disclosuretablerow) explicitly demonstrates an initially true expansion binding. A [firsthand forum follow-up from January 2024](https://www.hackingwithswift.com/forums/swiftui/fussing-with-table-on-macos/25250) describes successful nested per-node `@Bindable` expansion. Neither source tests the full Agent Monitor composition.

The user requested a standalone reproduction. The temporary standalone probe (commit `40e9f00`) used only SwiftUI and AppKit, stable synthetic identities, unshown windows and no production model. The environment was Apple Silicon, macOS 27.0.1 (26A434), Xcode 27.1 (27A9275), Swift 6.4 (swiftlang-6.4.0.34.1), Swift 6 language mode and an unoptimized build. The final run used normal local AppKit service access. No live workloads, provider helpers or physical input were involved.

| Roots | Disclosure levels | Expected expanded rows | Expected collapsed rows | Result for both binding modes |
| --- | --- | --- | --- | --- |
| 1 | 2 | 4 | 1 | Initial, collapse, reopen and remount passed. |
| 1 | 3 | 5 | 1 | Initial, collapse, reopen and remount passed. |
| 30 | 2 | 33 | 30 | Initial, collapse, reopen and remount passed; last leaf was outside the viewport before scrolling. |
| 30 | 3 | 34 | 30 | Initial, collapse, reopen and remount passed; last leaf was outside the viewport before scrolling. |

All 32 checkpoints passed using both a shared set of expanded IDs with explicit bindings and direct per-node `@Bindable` Boolean properties. The public backing outline's row counts and indentation matched the independently specified hierarchy. Clearing selection, scrolling and selecting the final leaf reported its exact ID through the SwiftUI binding. Every expected row count was already correct after the first explicit layout pass and remained correct after twenty task yields; no additional readiness wait was needed. Thus this fixture supplies no evidence for a deferred-update explanation of the earlier failure.

A disposable negative-control copy forced shared-set child bindings to return false while keeping the expected expanded hierarchy unchanged. It exited with status one and rejected all twelve affected expanded checkpoints; collapsed checkpoints and the unmodified per-node cases passed. This qualifies the missing-descendant oracle without treating an intentionally broken binding as a SwiftUI failure. The temporary negative source and executables were removed after extracting these results.

Conclusion: the alleged nested-expansion failure was not reproduced in this isolated fixture. Initial expansion, offscreen descendants and table recreation are not sufficient conditions for the reported failure on this toolchain. The earlier integration's binding, identity, composition or harness behavior remains unresolved; these are possible investigation areas, not demonstrated causes. The existing AppKit bridge remains unchanged. Its regression tests establish its behavior, not that SwiftUI cannot meet the requirement. This probe does not establish full production interaction, physical keyboard delivery, VoiceOver or behavior on other OS/toolchain versions.


## SwiftUI following-root triage — 2026-10-27

The user requested triage of the discrepancy between the recorded integration failure and the passing standalone control above. The failed pre-bridge SwiftUI source and its test log were not recoverable from committed/reflog/unreachable Git objects or surviving build logs. The investigation therefore reconstructed the integration using the current production `MenuBarModel.report.overview`, `ContributorID` values, disclosure methods, labels and the existing synthetic `nativeOverviewFixture`; it cannot establish byte-for-byte equivalence with the historical attempt.

The reconstruction reproduced the reported symptom. Opening `More processes`, its last session and that session's contributor before mounting a SwiftUI table gave 25 native rows where shared `visibleRows` expected 27. The missing rows were the expanded session's contributor and process at depths two and three. Shared expansion state remained unchanged. Both inline and recursive `TableRowContent` builders failed initially, and replacing live expansion bindings with `.constant(...)` did not change the failure. Collapsing/reopening the enclosing section restored all 27 rows; a subsequent snapshot refresh preserved them. The temporary integration probe (commit `89632ab`) kept the recursive version and both binding modes, with a known-issue matcher restricted to that initial missing-descendant signature.

Reduction identified the decisive variable in these fixtures: a following top-level sibling. The standalone probe in commit `89632ab` had two arms differing only by an appended collapsed root. Existing node IDs and expansion bindings do not change. Both use only SwiftUI/AppKit and fixed synthetic data on the same macOS 27.0.1 / Xcode 27.1 / Swift 6.4 environment recorded above.

| Standalone arm | Initial/remount | Collapse/reopen | Overall |
| --- | --- | --- | --- |
| Expanded branch last (control) | All 16 checkpoints pass. | All 16 checkpoints pass. | 32/32; exit zero. |
| Add one following root | All 16 checkpoints omit nested descendants. | All 16 checkpoints pass. | 16/32; exit one as the reproduced failure. |

The failures occur with both shared-set and per-node `@Bindable` expansion state, one or thirty original roots, and two or three disclosure levels. In the smallest case, the required order is parent → child → two leaves → following root (five rows); SwiftUI reports only parent → child → following root (three rows), despite both expansion bindings being true. All five rows fit the viewport, so virtualization/offscreen placement is not required. At three disclosure levels the same case produces three rows instead of six. Recreating the table repeats the loss, and a two-second readiness wait does not restore it.

Additional reductions confirmed the class: preceding siblings alone pass; a following sibling fails; giving surrounding siblings children of their own still fails; using ordinary `TableRow` leaves in recursive content still fails. A parent containing many sibling children passes when it is the only root. Value-type rows and an async-main lifecycle also pass in that control shape. These comparisons rule out those factors as necessary causes within the tested fixtures. The historical standalone fixture missed the defect because its expanded branch was always the final root.

The observable failure locus is SwiftUI `Table`/`DisclosureTableRow` initial hierarchy reconciliation: the backing outline does not reflect true descendant expansion bindings for the tested non-final expanded branch. This is a reduced framework-level reproduction, not an assertion about Apple's internal implementation or an Apple-acknowledged bug. It reproduces the integration symptom with and without production state, and predicts the three-level and remount failures. The unavailable original source limits the conclusion about the exact historical attempt.

The retained AppKit bridge passed the existing hierarchy/selection, offscreen-restoration and refresh/scroll guards alongside the reconstruction. The final targeted Swift Testing run passed with two explicitly recorded known issues from SwiftUI's initial reconciliation; those known issues are not successful SwiftUI restoration checks. No production UI was changed. Reordering contributors solely to place the expanded branch last would violate the user's chosen order, and collapse/reopen is an observed recovery, not an accepted application workaround. Physical input and VoiceOver remain outside this headless result; other platform versions remain untested. Temporary variant sources, executables and raw output were removed after retaining this evidence.

## Hidden SwiftUI restoration prototype — 2026-10-27

The user authorized testing a hidden collapse/reopen and requested an interactive reproduction. The standalone demo in commit `bf198eb` compared two identical synthetic branches with only the root order changed. Its unshown-window guard observed sorted native row counts `[3, 5]` initially, `[2, 5]` after collapsing the failing Session A, `[5, 5]` after reopening and `[3, 5]` after recreation. The user ran the demo and confirmed seeing the issue on 2026-10-27. This supplies a physical-window confirmation of the original rendering defect, not acceptance of the hidden-restoration workaround or VoiceOver behavior.

A temporary restoration prototype reused the production-state reconstruction, with a local presentation gate that temporarily collapsed expansion bindings without writing user disclosure. A white initial cover or a snapshot of the previous table concealed intermediate rendering; accessibility exposure was suppressed until ready. It restored expansion, selected the exact process using public native selection, restored the clip origin and forced row layout while covered. This was a test-only experiment, not a replacement for the production AppKit bridge or a purely SwiftUI solution.

Binding-only selection did not restore the descendant selection in the synthetic trials, including a window ordered outside all screens; selecting a root succeeded there. Public `NSOutlineView.selectRowIndexes` restored the descendant and updated the local selection binding. An earlier version passed row/selection checks but drifted by 12 points in the short viewport and 48 points in the tall viewport after reveal. Lazy row geometry therefore needs settling under the cover; merely disabling animation or performing two binding writes does not establish invisibility.

The 24-checkpoint matrix covered 420-point width, 240/560-point heights, three repetitions and initial mount/remount/refresh/reordering. Row-depth, selection, disclosure, covered-pixel and numeric scroll-position checks passed after covered layout settlement. A stronger before/after remount image comparison failed all six remounts in both debug and optimized builds, despite equal clip origins. The optimized trial's mount/collapse, expansion, selection/layout and reveal phases totaled 92.6–205.2 ms (median 171.7 ms); this includes forced bitmap rendering/encoding and excludes separate audit snapshots/comparisons, so it is not a production latency benchmark. Expansion required no timed waits. Stabilizing the previous frame did not fix the mismatch; preserving a visible-row anchor reduced failures to three but did not establish invisible restoration. The repair prototype was therefore not adopted or retained as application machinery.

The user questioned why the table should be recreated and suggested hiding it instead. The actual trigger is the conditional report/inspection branches in [MenuBarView](../../Sources/AgentMonitorMenuBar/MenuBarView.swift), not an inherent diagnosis or review requirement. Fresh overview state starts collapsed. User-expanded branches survive in the model when report content is removed, so returning requires a new native table to initialize expanded. Keeping the same table mounted while presenting inspection above it avoids this particular initialization path. This remains a test-only alternative; no production lifecycle or control change has been made.

The temporary lifecycle probe in commit `e15d9af` started the production-state reconstruction collapsed, opens each level in sequence and selects/scrolls to a process. The red variant conditionally replaced the table and failed native identity and rendered-frame checks. The green variant keeps the table in a stable `ZStack`, uses opacity to hide it, disables it, excludes hit testing/accessibility and places synthetic inspection content above it. The final debug run passed five targeted tests with the two existing, explicitly expected initial-expansion known issues. This fixture uses a 420 × 240-point unshown window; it does not exercise the actual diagnosis/review controls, hidden keyboard focus, VoiceOver, dark appearance or all other view recreation paths. Production adoption therefore requires wiring and testing those lifecycle/focus boundaries; this result supports retention as the simpler next direction, not a blanket SwiftUI correctness claim. Temporary restoration sources, captures and timing logs were removed after retaining these findings; the demo bundle remained local for the user’s check and was removed with the later adoption cleanup.
