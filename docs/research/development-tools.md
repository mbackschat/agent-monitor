## Grouping measurement — 2026-10-15

The Performance Audit workflow was applied to the repeated getter found in the first trial. A synthetic debug-build microbenchmark on macOS 27.0.1, Swift 6.4 and Apple Silicon compared the previous two-read expression with one local read of the same production `LiveReportState.groups` getter. Five samples per variant, alternating order, each ran 100 repetitions; each synthetic session had five processes. Median totals for 10/100/1000 processes were 6.902/98.753/951.034 ms for two reads and 3.561/50.328/472.095 ms for one. [Raw measurements](native-grouping-2026-10-15.json) retain the values; [the opt-in benchmark](../../Tests/AgentMonitorMenuBarTests/MenuBarPerformanceTests.swift) retains the fixture and checksum guard. These are grouping-expression timings, not full rendering, scrolling, release-build or energy measurements.

Inference: computing the groups once per report render removes confirmed redundant work without introducing cache invalidation state. The normal small fixture saves only about 0.033 ms per evaluation in this run, so this does not establish a perceptible speedup. The larger fixtures indicate scaling cost, not a claim that users normally have hundreds of heavy agent sessions.

## Content-sizing application — 2026-10-15

The sizing regression independently reproduced a one-process panel staying 560 points tall. Content measurement plus a capped scroll area produced an inspected three-process render of approximately 350 points, with disclosure-growth/collapse checks. A non-visible `NSPopover` initially reported zero content size when only the hosting controller's preferred-size option was set. Explicitly initializing the hosting view's fitting size and reporting root geometry to the popover supplied a verifiable size handoff. This is offscreen layout evidence, not live menu anchoring or VoiceOver evidence. The performance skill's warning about geometry feedback was useful here: measurements use equatable size values and skip unchanged AppKit sizes.

Retaining the intrinsic-size constraint was necessary: disabling every hosting sizing option made later fitting-size reads return zero. The final offscreen test verifies both the initial list and a transition to action review. This is a concrete limit of generic advice to reduce hosting constraints; fewer constraints are useful only if the required sizing contract remains intact.


## Stable inspection correction — 2026-10-15

The user clarified that the panel must retain its height as content changes; extra room should come from an explicit user choice. This supersedes the earlier content-fitting interpretation, without changing the compact row-density requirement. The previous content-measurement wrapper coupled disclosure and sample membership to outer geometry. Regression checks reproduced height changes for both sparse content and expanded multi-process groups. The fixed outer frame and flexible inner scroll area separate these concerns.

The SwiftUI view-refactor skill was useful for keeping size choice and pause state in the existing AppKit-owned model, with views expressing controls. The Swift Testing skill's parameterized cases cover all three size choices and four terminal widths. Neither skill supplies an inspection UX contract: the user's fixed-height requirement settles that choice. The existing neutral freeze state already holds the displayed snapshot and the latest pending update, so a second native freeze implementation would duplicate ownership.

The TUI's frozen indicator followed interval/sort text and was truncated at 40 columns. Moving the paused timestamp and resume hint to the front retains both at the smallest supported width. A subsequent regression check exposed filter clipping at 120 columns; omitting the application name and update counter from the paused heading preserves the filter text without adding header rows. Inference: explicit Pause/Resume is more predictable than hover-triggered freshness changes; whether users need a separate order-only lock remains an empirical question. No hover behavior or order-only lock was introduced.

## Menu tracking and explicit selections — 2026-10-15

The user reported intermittent first-click failures and submenus closing during report updates. Source inspection found the SwiftUI menu reading the complete observable report struct; each sample changes that struct. Inference: this couples menu rebuilding to unrelated process updates. This identifies an invalidation path, not proof of SwiftUI’s internal tracking failure. The regression initially failed to find a persistent native pull-down control at first layout. Tests now exercise loading-to-empty, loading-to-results and membership changes against the production hosting view, plus a simulated tracking delegate lifecycle; physical click delivery remains outside their evidence.

The Xcode 27 macOS 27 SDK’s `AppKit.framework/Headers/NSMenu.h` declares `menuNeedsUpdate` for population and explicitly prohibits changing menu structure/items inside `menuWillOpen` and `menuDidClose`. The implementation uses those callbacks only to guard tracking. An initial test used `NSMenu.update()` as an opening surrogate; it did not invoke the population delegate and retained old checkmarks. Calling the actual population callback in the controlled test distinguishes delegate policy from real event delivery.

The [SwiftUI view-refactor skill](../../.agents/skills/swiftui-view-refactor/SKILL.md) helped narrow observation inputs and retain AppKit ownership. Its extraction advice alone was insufficient: the previously extracted menu still read the entire report. The [Swift Testing skill](../../.agents/skills/swift-testing-expert/SKILL.md) was useful for identity assertions, synthetic sample transitions and source-control delivery without sleeps. These tests do not establish keyboard focus or menu behavior on a physical display; no skill supplied evidence for that claim.
