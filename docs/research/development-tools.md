## Cross-host discovery

The inspected [Codex documentation](https://learn.chatgpt.com/docs/build-skills) describes `SKILL.md`, repository `.agents/skills` discovery and symlinked directories. [Claude documentation](https://code.claude.com/docs/en/skills) describes `.claude/skills`, symlinks and additional host-specific frontmatter. [Axiom's compatibility table](https://charleswiltgen.github.io/Axiom/start/codex-install#differences-from-claude-code) confirms that procedures represented as skills in Codex may be agents or commands in Claude.

Inference: portable prose and relative references can be shared, but that does not make hook configuration, MCP tools or agent execution equivalent. The repository's later cross-host discovery checks are recorded in the development guide, not established by this source comparison.

## First project trial — 2026-10-15

Applied `swiftui-view-refactor` and the code-first review path of `swiftui-performance-audit` at the `agent-scripts` revision above to Agent Monitor's native UI at commit `67dab94`. Read the view-refactor MV reference and the performance skill's understanding/improving SwiftUI summary. This was a source review, not an Instruments capture, UI automation run or controlled comparison against an unaided review. No performance improvement was measured and no application code was changed during the trial. Current installation and usage belong in the [development guide](../development.md#skills-shared-by-codex-cli-and-claude-code).

| Review lens | Concrete observation | Assessment |
| --- | --- | --- |
| View ownership and dependencies | [MenuBarDelegate](../../Sources/AgentMonitorMenuBar/MenuBarApp.swift) owns the observable model and handles show/close/quit. [MenuBarView](../../Sources/AgentMonitorMenuBar/MenuBarView.swift) receives it with `@Bindable`; [MenuBarProcessLabel](../../Sources/AgentMonitorMenuBar/MenuBarProcessLabel.swift) takes small value inputs. | The skill is useful for checking explicit ownership and subview boundaries. Its blanket preference for root `@State` and view orchestration must be qualified: the root owner here is AppKit, and moving collection into view tasks would conflict with the accepted lifecycle. |
| View decomposition | The native root contains both the monitoring list and the complete action/composer rendering. The process summary is already an extracted value-driven view. | Inference: dedicated action/composer subviews could clarify responsibilities when that UI changes. Splitting everything merely to meet a stylistic ordering rule would add churn without demonstrated benefit. |
| Repeated derived work | The populated report reads `model.report.groups` for `isEmpty` and again for `ForEach`. [LiveReportState.groups](../../Sources/AgentMonitorPresentation/LiveReportState.swift) rebuilds groups and sorts them on each access, and its `rows` getter also sorts. | Confirmed redundant computation in this render path. Its user-visible cost is unknown; this identifies a concrete measurement target, not an established CPU bottleneck. Any optimization belongs in a separate guarded change. |
| Observation and identity | `MenuBarModel` exposes the entire value-type `report` as one observed property. Row keys use session identities and process lifetimes rather than new random identifiers in the view. | Stable row identity matches the skill's advice. Inference: report mutation may invalidate broader UI than necessary; actual body-update frequency requires a trace. Existing generation UUIDs are cancellation tokens, not row-identity churn. |
| Layout ownership | Both the host's `contentSize` and the root view's frame specify 420 × 560. | A concrete duplicated sizing contract, relevant to the existing content-fitting question. Neither skill supplies menu-specific sizing or accessibility validation. |

Assessment: retain both as focused review aids. View Refactor helps reason about responsibility boundaries but its MV reference is opinionated and mostly illustrates iOS/SwiftData. Performance Audit provides a useful sequence from identifiable code paths to profiling and comparable measurements; its checklist is not proof that every listed pattern needs caching or refactoring. The trial supports their usefulness as prompts, not a quantified quality ranking.
