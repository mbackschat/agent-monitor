## Grouping measurement — 2026-10-15

The Performance Audit workflow was applied to the repeated getter found in the first trial. A synthetic debug-build microbenchmark on macOS 27.0.1, Swift 6.4 and Apple Silicon compared the previous two-read expression with one local read of the same production `LiveReportState.groups` getter. Five samples per variant, alternating order, each ran 100 repetitions; each synthetic session had five processes. Median totals for 10/100/1000 processes were 6.902/98.753/951.034 ms for two reads and 3.561/50.328/472.095 ms for one. [Raw measurements](native-grouping-2026-10-15.json) retain the values; [the opt-in benchmark](../../Tests/AgentMonitorMenuBarTests/MenuBarPerformanceTests.swift) retains the fixture and checksum guard. These are grouping-expression timings, not full rendering, scrolling, release-build or energy measurements.

Inference: computing the groups once per report render removes confirmed redundant work without introducing cache invalidation state. The normal small fixture saves only about 0.033 ms per evaluation in this run, so this does not establish a perceptible speedup. The larger fixtures indicate scaling cost, not a claim that users normally have hundreds of heavy agent sessions.

## Content-sizing application — 2026-10-15

An offscreen one-process panel remained 560 points tall; content measurement with a capped scroll area produced an inspected three-process render of approximately 350 points. Initializing the hosting view's fitting size and reporting root geometry supplied a usable handoff. These are offscreen layout observations, not live anchoring or accessibility evidence. The later [fixed-height requirement](native-menu-design.md#fixed-height-clarification--2026-10-15) supersedes content-driven outer resizing.

## Native menu and layout observations — 2026-10-15

During reports of intermittent first clicks and closing submenus, source inspection found the SwiftUI menu observing the complete changing report struct. That establishes an invalidation path, not the cause of SwiftUI's internal tracking behavior. The Xcode 27 macOS 27 SDK's `AppKit.framework/Headers/NSMenu.h` declares `menuNeedsUpdate` for population and prohibits changing menu structure/items inside `menuWillOpen` and `menuDidClose`. A controlled `NSMenu.update()` call did not invoke the population delegate; it was not an adequate surrogate for actual opening.

The user reported no visible status-icon tooltip. [Apple's status-item button documentation](https://developer.apple.com/documentation/appkit/nsstatusitem/button) explicitly supports `toolTip`, but API availability does not establish visible delivery. The hypothesis that frequent reassignment interfered with hover timing remained unverified; no live desktop inspection established it.

Historical offscreen fixtures measured a pin target at 28 × 28 points against a requested 32-point target, and “Memory · 10m” at 114 points inside a 104-point selector slot. Expanded keyboard help measured 305 points, then 233, against a 230-point bound. These are captured layout constraints, not evidence of physical pointer targeting, legibility or current dimensions. Accepted controls and sizing belong in the [native contract](../architecture.md#native-menu-bar-app).

## Test-value audit — 2026-10-26

Source review across the Swift test targets at revisions `79c9255` through `63d82b6` found recurring oracle weaknesses: unchanged inputs duplicated a case without exercising a new boundary; global conservation could pass with the wrong session assignment; an all-satisfy predicate could pass on an empty result; and JSON searches could match identity evidence outside the intended field. These are test-design counterexamples, not demonstrated product defects or measured suite speedups. Current regression procedures belong in [development](../development.md#choose-checks-for-the-change).

Concurrency assertions need evidence that the consumer or waiter actually entered the state under test; prebuffered events do not establish acquisition progress while a callback is held. A synthetic instant clock can also impose unintended ingress/publication pressure on a fixture intended to isolate consumer stalls. Queue occupancy and explicit publication acknowledgements distinguish those mechanisms; a missing final-scan sentinel alone cannot identify the original rejection stage.

Offscreen geometry and pixels establish specific rendered properties, not physical interaction or general legibility. Vision did not reliably recognize isolated zero glyphs in the inspected coverage render; distinct multi-digit values supported number-to-label checks, with observed i/l and bullet variation. Model-level assertions remain necessary for zero semantics. These observations do not establish native performance or accessibility acceptance.

## Verify scheduling and native OCR — 2026-11-01

[Verify run 41259618374](https://github.com/mbackschat/agent-monitor/actions/runs/41259618374) at `3a020ff` passed prerequisites, documentation, release-script checks and formatting, then failed its test step with 54 issues: 19 in the four `SimultaneousOwnershipTests` cases and 35 native issues, comprising 32 Vision `.nilError` errors and three focus/shortcut/pixel assertions. The workflow and release script still invoked plain `swift test`, bypassing the documented serial full-suite policy. AppKit tests share application state, and the ownership fixture's bounded worker gates expired during the concurrent run; neither failure calls for changing production collection semantics.

Local Debug validation with `--skip-build --no-parallel` and CI's synthetic-render options passed the three native non-OCR failures before stalling in OCR. A one-second sample of the owned helper found all 872 samples of its OCR thread inside `VNImageRequestHandler.perform` → TextRecognition → semaphore wait; MainActor was idle in its run loop. After stopping that owned run, separate serial validation passed 369 core, 306 CLI/presentation and 16 action tests. All four ownership cases passed in 0.819 seconds. The initial serial run had already passed eight TUI, six preview and ten capture tests. These results establish the scoped serial checks, not a complete native or hosted-CI pass. No product behavior changed in Mac, TUI, text CLI or JSON; the native label/resource-summary computations were made module-visible for direct tests.

Bounded subprocess checks against the synthetic panel image timed out after 12 seconds each with accurate recognition under forced CPU selection, default devices, legacy CPU-only selection, revision 2 and explicit English without language correction. Fast CPU recognition completed but misread identifiers and paths. A temporary switch of the shared OCR helper to fast mode then failed seven unchanged assertions across the adaptive-coverage and compact-session-label tests, including `/alpha/project` being read with `l` in place of `/`; the source change was reverted. The [independent xcode-27 runner investigation](https://github.com/LorcanChinnock/shot/pull/818) reports accurate-engine failure without a Neural Engine and a fast-mode fallback. The replacement checks use the actual native owner-label/visibility computations, shared presentation values, command-inspection state, native scroll offsets and existing geometry/pixel assertions. Exact owner/session and directory values remain asserted independently of rendering. An in-process accessibility experiment read ordinary AppKit text but returned no SwiftUI children from offscreen hosting views, including after hit testing/navigation queries and a bounded layout wait, so it was not adopted. No OCR engine or additional dependency remains. The removed pixel-transcription checks are not claimed as equivalent visual coverage: glyph legibility, exact painted truncation, label placement and physical accessibility remain render/smoke-review concerns.
