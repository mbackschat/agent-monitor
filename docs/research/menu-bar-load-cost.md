# Menu bar load collection cost

Observed 2026-10-15 on Apple Silicon (8 logical processors), macOS 27.0.1 and Swift 6.4. These are bounded read-only probes of the shared production sampler, not long-duration app energy measurements. No process identities, paths, environment values or transcripts are retained in the measurement files. The accepted behavior is in [architecture](../architecture.md#native-menu-bar-app); repeatable measurement and coverage limits are in [development](../development.md#menu-bar-app).

## Initial measurements and attribution

The initial opt-in all-agent summary used the existing per-target enrichment traversal. A standalone debug test-harness run of four 15-second samples consumed 4,847.791 ms of process CPU over 68.416 seconds (7.086% of one core). A subsequent instrumented run attributed 3,589.985 ms to 2,465 metadata reads and 60.453 ms to five resource snapshots, out of 5,068.165 ms total. This showed that changing cadence alone did not make the draft indicator inexpensive.

A synthetic fixture with one runtime and 100 detached workers reproduced 27,154 adapter recognition calls across its queries, executable-change and PID-reuse checks. The guarded implementation retains the full recognition set per unchanged executable/lifetime and rebuilds a live single-provider runtime index. The same fixture now requires exactly 103 calls, including both invalidations. Metadata and resolved session ownership are not cached; existing conflicting-provider and detached-runtime guards remain applicable.

A synthetic 200,095-byte argument buffer containing a long unused argument, a long unrelated environment value and one allowlisted marker took 526.018 ms for 100 parses before the change and 3.464 ms after it in debug builds. The parser now scans bounded byte ranges and decodes only requested arguments and allowlisted values. This microbenchmark does not measure native process access.

After those changes, an unrestricted debug test-harness run still consumed 3,658.444 ms over 66.249 seconds (5.522% of one core). A 20-second stack sample of a subsequent owned test helper, at 10 ms sampling intervals, recorded 142 of 198 metadata stack observations inside `Array.init(repeating:count:)` at the argument-buffer allocation. The stack sample is statistical evidence, not a precise per-operation time allocation. The reader now uses a temporary bounded raw buffer with bulk zero initialization and passes only the returned byte count to the parser. Zero initialization, same-user/lifetime verification and provider allowlisting remain intact.

The first probes ran inside the tool sandbox; the unrestricted post-parser run remained expensive, so sandbox enforcement did not explain the problem. Process populations and other machine activity varied between runs. Percentage comparisons across those runs are observations, not a controlled whole-app speedup claim.

A comparable unrestricted debug test-harness run after bulk initialization consumed 570.833 ms over 64.257 seconds (0.888% of one core), with 434.617 ms in 2,674 metadata reads. The earlier stack sample also showed 24 observations in `lstat` beneath `URL.init(fileURLWithPath:)` during executable recognition. These adapters need path components, not filesystem classification. Their URL construction now supplies `.notDirectory`, and nonterminal processes skip the extra terminal-provider lookup. Apple's [directory hints](https://developer.apple.com/documentation/foundation/url/directoryhint/inferfrompath) distinguish filesystem checks from explicit directory knowledge; [Swift Foundation source](https://github.com/swiftlang/swift-foundation/blob/main/Sources/FoundationEssentials/URL/URL.swift) corroborates that URL construction can request filesystem checks. The online source was inspected on this date but is not pinned to the installed framework; the local stack is the direct evidence of this call path.

A standalone harness compiled directly from the same core sources measured 763.630 ms over 63.201 seconds in an unoptimized build (1.208% of one core) and 361.819 ms over 63.817 seconds with `-O` (0.567%). These runs included bulk initialization but preceded the explicit URL directory hints. They used a smaller harness than the Swift Testing probe and are not directly interchangeable with its numbers. The normal local bundle script now selects an optimized build; debugger-oriented builds remain available as documented in [development](../development.md#menu-bar-app).

The final unrestricted debug test-harness run consumed 433.237 ms over 64.198 seconds (0.675% of one core), including five resource snapshots and 2,689 metadata reads. The final optimized [standalone probe](../../Tools/LoadProbe/LoadProbe.swift), compiled from the production core sources, consumed 191.076 ms over 63.130 seconds (0.303% of one core). [Raw results](menu-bar-load-cost-2026-10-15.json) preserve the measurement stages, harnesses and restrictions. The debug-to-debug comparison shows a large reduction; the optimized number also changes compiler configuration and harness, so it is not a controlled speedup ratio against the initial debug result.

## Measurement limits

The test harness measures process CPU (user and system) and elapsed time, including baseline acquisition and four samples. It excludes menu-bar drawing, full app startup, user actions and wakeup accounting. The synthetic parser probe ran alongside semantic tests; its timing is useful for identifying the large byte-scanning cost but is not a precision benchmark. The test-library helper required XCTest framework/library paths when run directly; failed helper launches produced no measurements. App CPU/wakeups over a sustained closed-panel interval and behavior on other machines remain empirical questions.

## Native row command stall — 2026-10-24

The user reported the optimized app at `458e8dc` as barely usable and slow to open, then quit it. A read-only `ps` snapshot showed 98.9% of one CPU core. A nominal three-second stack sample at five-millisecond intervals placed all 322 main-thread observations inside SwiftUI row layout, including context-menu construction, `MenuBarModel.canBegin`, `visibleRowIDs`, `LiveReportState.projection`, `children(of:)` and repeated global row sorting. Both dedicated collection threads were waiting on their worker semaphores in all 322 observations. This sample identifies a main-thread bottleneck; it does not establish that macOS assigned menu bar apps low scheduling priority or that collection has no cost.

The mechanism was repeated full-table projection inside each row's command predicates. Each focus/message/terminate/PID-copy check rebuilt visible rows, session groups and sorted process lists; session projection additionally recomputed global displayed membership for each group. The work multiplied with the number of rows/groups before SwiftUI could finish layout. This was an existing presentation cost exposed by the fast, unfiltered collector; changing thread priority or suppressing measurements would not remove it.

The retained [synthetic measurements](native-row-commands-2026-10-24.json) evaluate exactly those predicates for 50 and 150 synthetic processes, with one session per process, in both grouping modes. Three passes were recorded per case using the same debug configuration. With 150 session rows, each pass took 25.74–36.35 seconds before the fix and 0.86–0.93 milliseconds after it. The process-list case fell from 1.96–2.47 seconds to 0.82–0.93 milliseconds. The shared projection now constructs child membership once; the native host reuses an immutable index for the displayed snapshot/order/pins/disclosure. Selection and history-only changes reuse it; fresh displayed data and structural changes replace it.

These timings isolate command predicates and exclude index construction, full SwiftUI rendering, native acquisition and provider resolution. They establish removal of the repeated traversal, not a whole-app speedup ratio or sustained CPU guarantee. Live responsiveness after replacement remains a user check. The local stack trace is temporary; the portable dataset retains only aggregate observations.

A second offscreen check found eager SwiftUI row construction still scaling with the total list size after indexing. Before lazy row stacks, a 1,000-process synthetic list took 674–861 ms per refresh in debug; lazy stacks reduced the corresponding final run to about 51–54 ms. The filtered fixture has **ten displayed rows**, backed by 150 observed processes in ten sessions: command checks took 0.049–0.060 ms and full offscreen refreshes, including model/index rebuilding, took 8.86–10.44 ms. Hidden observations remain in totals and cannot become actionable process rows through the filtered view. The 1,000-row case is a stress test, not an assertion about the user's window; its actual row count was not captured. The same lazy construction applies inside expanded sessions: an additional fixture with one expanded session and 150 children refreshed in 10.34–11.37 ms. Initial layout and individual refresh timings are retained in the dataset. Offscreen tests do not measure physical event delivery or establish post-fix live CPU use.

Source inspection at `8244fe3` established the following mechanisms:

- [Thresholds and ProcessScope](../../Sources/AgentMonitorCore/Model.swift) default resource thresholds to zero and admit agent scope when provider or runtime evidence is present. Exact session resolution is not required, and zero CPU is not a liveness test.
- [Native collection](../../Sources/AgentMonitorMenuBar/MenuBarCollection.swift) uses that default agent scope. [AgentLoadSummary](../../Sources/AgentMonitorCore/AgentLoadSummary.swift) deduplicates observed agent-associated process lifetimes, and [MenuBarIndicator](../../Sources/AgentMonitorMenuBar/MenuBarIndicator.swift) derives its count from unfiltered observations and the current window. The badge is a population count, not a count of busy processes or independent sessions; historical contributors in that window can count too.
- [AccountingWindow](../../Sources/AgentMonitorCore/AccountingWindow.swift) retains historical contributors for the enclosing delivered window; a subsequent window need not retain them. [ReportHistory](../../Sources/AgentMonitorPresentation/ReportHistory.swift) stores scalar trends rather than browsable per-session/per-worker history. This explains why a measured burst can disappear from process inspection on the next update without proving that its measured CPU was discarded from the earlier window.
- Rounded display values do not establish exact zero. A low CPU value can round to `0.0%`, and a footprint below approximately 50 MB can round to `0.0 GB`; unavailable footprint is represented separately. The crop does not expose underlying readings or exit evidence.

The review's whole-delivered-window recommendation needs qualification. [Pipeline resolution](../../Sources/AgentMonitorCore/IndependentMonitoringPipeline.swift) closes consecutive scan-index windows, but presentation can coalesce them into arbitrarily wider deliveries within its capacity limit. [CounterWindow](../../Sources/AgentMonitorCore/CounterLedger.swift) explicitly separates contributions whose opening precedes the retained baseline. A contribution closing in a later window can span an earlier window after missing reads. Whole-window eviction therefore does not eliminate crossing/recovered CPU, and enclosing durations are not additive. The revised proposal chooses complete pre-coalescing core windows, keeps endpoint eligibility/recovery rules and states how oversized recent ranges and capacity gaps are displayed.

The proposed kernel-peak label “since last exec” and executable-change label “spans exec” would overstate present evidence. The [owned kernel-peak probe](cpu-accounting.md#kernel-memory-high-water-mark) demonstrated reset on exec but did not supply a peak timestamp or verified execution epoch. Path/name changes are observations, while unchanged paths cannot exclude same-path exec. The revision uses last-observed kernel task peak with timestamp/epoch uncertainty and an observed executable-change label. It does not move older kernel peaks into recent-window maxima.

The review's other clarifications are retained in the revised contract: disappearance is global absence rather than a session change; unidentified unreadable PIDs are observation counts, not workers; only adapter-recognised agent runtimes are excluded from the worker population; coalesced CPU shows its actual duration; examples distinguish processes from workers; root groups preserve exact thread identity; and optional session memory peaks remain gated on original per-scan observations and asynchronously available attribution. Numeric ranking/hysteresis floors and record/text caps remain proposed constants, not validated usability or heap guarantees. The review did not establish new attribution, coverage or performance results.

A subsequent read-only consistency review identified an interaction between memory summaries and late attribution: reducing pending readings of 100 MB and 80 MB to their maximum loses the second session's value if a valid revision later splits those observations across owners. Removing a category winner similarly needs its runner-up. The contract at `84867ae` therefore required original memory observations within the history/revision budget, recomputation, whole-unit eviction or explicit incomplete/unavailable maxima when context was lost. The example is a design counterexample, not a measured workload; the capacity re-review below supersedes that retention choice by deferring retroactive revisions.

### Capacity re-review — 2026-10-24

The user supplied a re-review of `84867ae`, accepting B1–B4 and the earlier qualifications but identifying N1: retaining every footprint observation and contribution for an undefined revision horizon makes the proposed 60-second target incompatible with 65,536 records at normal populations. The reviewer also identified missing history scope, current-graph root regrouping, unnecessary previous-run inspection and duplicated approval status in the canonical instructions. These findings were checked against the current source; no new workload capture or performance measurement was run.

At a nominal 100 ms cadence, 60 seconds contains 600 scans. Assuming one footprint observation and one contribution per identified process per scan, an illustrative stable population of 90 requires 108,000 records, and 613 requires 735,600. The bare cap would cover at most 36.4 and 5.35 seconds respectively, before other context. The 90-process example is a design population, not an exact earlier badge reconciliation; 613 comes from the earlier single same-user process-table check. The arithmetic is conditional, not measured retained duration.

[Pipeline resolution](../../Sources/AgentMonitorCore/IndependentMonitoringPipeline.swift) enriches each scan and runs due provider listings before appending its findings to the accounting window; `findings(scope: .allProcesses)` supplies that accumulation. Frozen labels therefore already include available resolved evidence for that scan. Later registry listings do not prove earlier ownership. [CounterWindow](../../Sources/AgentMonitorCore/CounterLedger.swift) supplies the endpoint rule needed to separate within-unit CPU from crossing contributions. These mechanisms support the narrower immutable-history recommendation without claiming that all delayed evidence is harmless or that unknown worker CPU is fully attributed.

N1 is accepted. The [revised proposal](../architecture.md#immutable-compact-history) drops retroactive live-history revisions in this delivery, scopes retention to the collector's configured population and seals compact records per lifetime/frozen semantic category. Individual earlier-opening CPU intervals retain IDs/endpoints. Whole-unit suffixes preserve exact summed eligible CPU and maxima under these immutable labels; arbitrary within-unit cuts and later reclassification are deliberately unsupported. One stable category per lifetime per one-second unit gives 5,400 or 36,780 compact records per minute in those examples, before crossing intervals, context, churn, category changes and held projections. This removes the mandatory scan-rate multiplier; the text/heap/total record budget still needs validation.

The initial projection of incoming labels and root corroboration is frozen with the corresponding observation; present-day `SessionGrouping` corroboration cannot regroup history. The revision discards older history on run/scope replacement, keeping only within-run retention-gap segments, and removes the authorization-status clause from `CLAUDE.md` while preserving its disclosure invariant. The broader accounting/recording revision contract remains separate. A future need for retroactive recent-history updates must be justified by owned-workload evidence and an explicit numeric horizon/budget, rather than reintroducing unbounded per-scan retention implicitly.
