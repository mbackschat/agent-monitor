# Existing solutions and reusable code

Research date: 2026-10-14. This is a source review, not an installation, runtime benchmark, or endorsement. GitHub default-branch trees, license contents, repository metadata, and release metadata were fetched directly; important implementation links below are pinned to the observed commits. A recent push demonstrates activity, not correctness. No fetched activity date was later than the research date.

### Gaps

No candidate was installed or run against the user's active sessions. Correctness under multiple sessions in the same cwd, resume/clear, PID recycling, privilege changes, environment scrubbing, very short processes, and shared MCP services remains unverified. CPU overhead, battery impact, and memory footprint claims are not comparable benchmarks. Source review did not establish a complete existing solution for every one of these cases.

The inspected sysinfo implementation protects its own process refresh against a changed process start time, refreshes CPU from deltas, reads cwd using `PROC_PIDVNODEPATHINFO`, and obtains arguments/environment using `KERN_PROCARGS2`. These are concrete implementation assets, not inferred macOS capabilities. [Backend source](https://github.com/GuillaumeGomez/sysinfo/blob/515e40d86be11dd9ffb4aa073888eb0a03f4dc0b/src/unix/apple/macos/process.rs).

The current macmon sampler distinguishes footprint-based native process memory from RSS fallback data and measures CPU across sampling intervals. It also tests the imported rusage structure's size and offsets. This is useful evidence for treating metric provenance and foreign-function layout validation as part of the data contract. [Process sampling source](https://github.com/vladkens/macmon/blob/eb6ab687abbedb3ad21f69c6c04365ea1a3ebe00/src/app/procs.rs).

## Source mechanisms and maintenance evidence

### Cited Findings

1. **Session stamps and socket availability.** Claude documents `CLAUDE_CODE_SESSION_ID` in tool, hook, and stdio MCP subprocesses, with clear/resume and already-running MCP caveats. The messaging socket exists only for sessions binding an inbox, from v2.1.224 onward. This qualifies claude-top's broad README claim that every child has a socket stamp. [Official environment reference](https://code.claude.com/docs/en/env-vars), [claude-top environment reader](https://github.com/mbrummerstedt/claude-top/blob/d088212b58ad7a9b8d424ca283e4aef90224227e/Sources/ClaudeTopKit/ProcessEnvironmentReader.swift).
2. **Explicit evidence classes.** Tidewake's rules use `CLAUDE_CODE_SESSION_ID` and `CODEX_THREAD_ID`; its classifier distinguishes known leftovers, detached work, uncertainty, and path-based suspects. The Codex variable in these rules is upstream application usage evidence, not by itself an official stability guarantee. [Rules](https://github.com/berkkorkmaz/tidewake/blob/7dcb8d83a5b9c5e869c3b39ba75c2fc12d1f7076/internal/rules/pack.json), [classification](https://github.com/berkkorkmaz/tidewake/blob/7dcb8d83a5b9c5e869c3b39ba75c2fc12d1f7076/internal/attrib/attrib.go).
3. **Lifetime-aware caches.** Corral caches executable paths, terminals, and arguments against PID plus start time, and uses kernel wall-clock start information rather than deriving age across sleep from a monotonic clock. [Scanner](https://github.com/popyapp/corral/blob/39ba7680fb18f79b9f824274d8446e8e18d16c8b/Sources/Corral/ProcessScanner.swift).
4. **Interval measurements.** Claude-top reads cumulative user/system CPU time and RSS through `PROC_PIDTASKALLINFO`, then calculates deltas; a 25% threshold needs this interval definition and a specified normalization. Its source deliberately distinguishes missing deltas from valid zero values. [Process table](https://github.com/mbrummerstedt/claude-top/blob/d088212b58ad7a9b8d424ca283e4aef90224227e/Sources/ClaudeTopKit/ProcessTable.swift), [delta calculation](https://github.com/mbrummerstedt/claude-top/blob/d088212b58ad7a9b8d424ca283e4aef90224227e/Sources/ClaudeTopKit/AttributionEngine.swift).
5. **Environment allowlisting.** Claude-top extracts an allowlist from raw environment entries instead of retaining every variable. Tidewake and agent-top show that useful ownership context can be separated from transcript content and resource sampling. [Environment reader](https://github.com/mbrummerstedt/claude-top/blob/d088212b58ad7a9b8d424ca283e4aef90224227e/Sources/ClaudeTopKit/ProcessEnvironmentReader.swift), [core interface](https://github.com/kannandreams/agent-top/blob/5961bf0087d9f827bc4963a8d00c3780000a3ad1/crates/agent-top-core/README.md).

### Gaps

Current README claims and implementation behavior can diverge, and default branches can outpace released builds. This review identifies one concrete divergence to avoid propagating: the universal Claude socket-stamp assumption versus the official conditional socket contract. No code was imported, tool installed, user process inspected, or process terminated for this report.

## Agent-oriented CLI investigation — 2026-10-16

This follow-up examines how a coding agent can learn and consume a local resource-diagnostic CLI. It does not revalidate the 2026-10-14 license, release or compatibility findings above. Public primary documentation/source was inspected without installing or running comparison binaries. No live process diagnosis, messaging or termination was tested. The resulting [finite CPU diagnosis contract](../architecture.md#finite-cpu-diagnosis) was implemented on 2026-10-17; that later outcome does not revalidate this dated investigation.

### Local source observations and limited agent experiment

Local source observations refer to Agent Monitor base commit `8e9387c`. [AgentMonitorCommand.swift](../../Sources/AgentMonitor/AgentMonitorCommand.swift) documents one report after a one-second baseline interval, yet leads its examples with `--json --samples 0 --interval 2`, an unlimited stream. [Options.swift](../../Sources/AgentMonitor/Options.swift) includes lengthy TUI keys in top-level help; it documents CPU as one-core percentage, decimal GB physical footprint, strict CPU-or-memory thresholds and same-user scope. These facts distinguish workflow prioritization from missing syntax documentation.

[JSONReport.swift](../../Sources/AgentMonitorPresentation/JSONReport.swift) emits schema version 2, thresholds, interval, counts and findings, with `attributionMeaning` set to `launchOrigin`; it does not encode selected scope or reasons for provider lookup failures. [MonitoringSession.listSessions](../../Sources/AgentMonitorCore/MonitoringSession.swift) catches noncancellation registry errors, binds nil and loses the reason. The [architecture's attribution contract](../architecture.md#harness-adapters) distinguishes provider-owned interpretation; current runtime registry evidence is not simply an inherited launch marker.

[NativeProcessReader.swift](../../Sources/AgentMonitorCore/NativeProcessReader.swift) filters readable process records by current UID and verifies PID/start identity around sampling. Its unreadable count includes failed identity reads before UID is known and identity races, while a failed resource read can yield a retained sample with nil CPU/footprint without incrementing that count. Therefore this counter is neither complete whole-system visibility nor a count of every missing resource metric. Sampling can miss processes that start and exit between observations. The existing report contains no exact host-wide CPU utilization denominator.

A fresh `gpt-6-luna` helper at medium reasoning received the user CPU question and could inspect only executable help, JSON schema, version and subcommand help; repository reading, sampling and actions were excluded. It read `--help` (4,308 bytes) and `--json-schema` (4,763 bytes), then redundantly ran `--help | wc -c`, which returned 4,308. That was three executable invocations and 9,071 unique help/schema bytes, **not measured model tokens or billing**. It proposed `agent-monitor --all-processes --cpu 1 --memory-gb 1 --samples 1 --json`, correctly retaining same-user and launch-origin limitations but independently choosing low thresholds and one report. Its criticism that one-sample semantics were absent was incorrect: current help documents them. No live diagnostic effectiveness was evaluated.

### Inferences

- Discovery of an executable, learning its semantics and interpreting its output are separate tasks. A PATH entry alone does not establish spontaneous selection by an agent; agent-browser's documented integration routes explicitly name the executable or supply a discovery stub. [Agent integration](https://github.com/vercel-labs/agent-browser#usage-with-ai-agents).
- Focused local guidance and a compact finite result could reduce exploratory calls, but the comparison and constrained helper run do not measure that reduction. A schema alone cannot select the observation window or explain ownership uncertainty.
- A top-N result needs pre-truncation totals and omission counts. Otherwise an agent can mistake displayed contributors for the measured population. Time-weighted observations and lifetime coverage are needed before comparing partial-lived processes with full-window measurements.
- Read-only diagnosis can consume CPU and launch provider lookup helpers; it is not synonymous with zero connection or metadata side effects. Resource counters explain measured consumers, not necessarily why their application code is busy.

### Unresolved empirical questions

No measured cold-use/repeat-use call or token distribution establishes optimal guide size, observation duration or row limit. Comparison binaries' latency, permission handling and partial-output behavior remain untested. Whether representative agents correctly interpret empty, ambiguous and partial observations remains unmeasured. The helper exercise cannot establish diagnostic accuracy because it never sampled. No reviewed source proves that all inaccessible processes or short-lived contributors can be accounted for by periodic same-user collection.

## Interactive diagnosis assessment — 2026-10-17

This assessment inspected Agent Monitor's implemented diagnosis at commit `f02fbcd` and its existing interactive contracts. It did not inspect live workloads or run a provider listing, and it does not revalidate the upstream comparisons above.

### Local observations

- [CPUDiagnosisWindow](../../Sources/AgentMonitorCore/CPUDiagnosisWindow.swift) retains per-lifetime CPU contributions across its finite run and ranks CPU-seconds before truncation. [CPUDiagnosisSession](../../Sources/AgentMonitorCore/CPUDiagnosis.swift) enriches returned contributors after the last scan; contributors missing from that scan retain CPU but have unavailable attribution. Neither type depends on a UI or Argument Parser.
- [MonitoringSession](../../Sources/AgentMonitorCore/MonitoringSession.swift) publishes current findings; [LiveReportState](../../Sources/AgentMonitorPresentation/LiveReportState.swift) maintains selection and disclosure for the live table. [ReportHistory](../../Sources/AgentMonitorPresentation/ReportHistory.swift) retains scalar all-agent summaries, not per-process interval contributions. These are separate populations and retention contracts, as documented in [architecture](../architecture.md#resource-history).
- Native and TUI tables default to five-second sampling, while diagnosis takes three one-second waits. A finite diagnosis launched later cannot reconstruct CPU from a process that disappeared before its baseline. Host/process coverage and missed exited work retain the limitations in [CPU accounting research](cpu-accounting.md).

### Inferences and unresolved questions

An explicitly requested finite result could make contributors observed during that new run easier to inspect in either UI, while keeping the live table's values familiar. It cannot recover a burst that ended before invocation. A rolling view would need new retention and coverage semantics; existing report percentages and scalar history cannot correctly supply it. The [interactive proposal](../proposals/interactive-cpu-diagnosis.md) records the resulting design judgment, not a measured usability finding.

No UI evaluation establishes whether users prefer a separate finite view, a rolling ranking or the existing table. Additional collection alongside ordinary monitoring would add work; its latency, responsiveness and sustained cost have not been measured. A fixed result is easier to retain than current action eligibility: historical identities must never gain actions merely because their PID is currently occupied.

### Review follow-up — 2026-10-17

Source observations rechecked at `1c7b4ee`: [NativeProcessReader.snapshot](../../Sources/AgentMonitorCore/NativeProcessReader.swift) excludes supplied PIDs, not their descendants. [CPUDiagnosisSession](../../Sources/AgentMonitorCore/CPUDiagnosis.swift) performs its provider lookups after the final scan, whereas a UI's independent [MonitoringSession](../../Sources/AgentMonitorCore/MonitoringSession.swift) can perform lookups concurrently. That session's listing cadence is once a minute after the initial or newly needed runtime lookup; each diagnosis has its own lookup outcomes and does not consult the cadence. The production registry command has a three-second timeout per query.

Cancellation is cooperative, but not limited to boundaries between whole commands: [BoundedCommand](../../Sources/AgentMonitorCore/BoundedCommand.swift) checks task cancellation inside its read loop, whose poll waits at most 50 ms, and during process-exit waiting. Owned subprocess cleanup also waits for termination. A synchronous native read cannot be interrupted mid-call. The diagnosis now checks cancellation after scans and enrichment and before result publication; fake-reader regression tests cover cancellation during the final scan, metadata observation and lookup. These checks do not establish UI cancellation latency.

Inference: a concurrent UI collector or action transport can contribute monitor-owned helper CPU to a diagnosis, possibly carrying inherited provider markers. A direct observed parent PID matching the still-live monitor can identify a helper even though the monitor is absent from the sampled graph; observed descendants of that exact helper lifetime can inherit the evidence. Reparenting and scan gaps prevent a complete exclusion guarantee. Flagging observed helpers while retaining their measured CPU avoids silently changing population accounting; that is a proposed UI policy, not shipped behavior or measured overhead.

The one-second live interval is an existing, cheaper alternative for freshness. It still publishes latest-interval findings and does not retain departed contributors or accumulate their CPU-seconds. Whether the separate finite view is worth its extra scans remains an open usability and cost question.

Source correction checked at `b4c95ba` on 2026-10-17: [DiagnoseCPUCommand](../../Sources/AgentMonitor/DiagnosisCommands.swift) excludes `getpid()` from every scan, and [Monitor.ingest](../../Sources/AgentMonitorCore/Monitor.swift) creates a parent link only when that parent appears in the same snapshot. Consequently, the original proposed ancestry chain could never reach the excluded monitor. `ProcessSample.parentPID` remains available without a corresponding graph node; matching it against the running interface's own PID avoids that missing edge. This corrects the proposal mechanism, not shipped attribution behavior; no live process probe was run.
